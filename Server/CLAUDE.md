# Server/CLAUDE.md

이 문서는 `Server/` 디렉토리에서 작업할 때 참고하는 가이드입니다. 프로젝트 전체 구조는 [루트 CLAUDE.md](../CLAUDE.md)를 참고하세요.

## 빌드 & 실행

Visual Studio 2022에서 `Server/Server.sln`을 열거나 `msbuild`를 사용해 다음 실행 프로젝트 중 하나를 빌드합니다(정적 라이브러리 `ServerCore`·`BotEngine`은 참조로 함께 빌드됨). 솔루션 구성은 `Debug|x64`, `Debug|x86`, `Release|x64`, `Release|x86` 4가지입니다.

```
msbuild Server.sln /p:Configuration=Debug /p:Platform=x64 /t:GameServer
msbuild Server.sln /p:Configuration=Debug /p:Platform=x64 /t:LoadTest
msbuild Server.sln /p:Configuration=Debug /p:Platform=x64 /t:DummyClient
msbuild Server.sln /p:Configuration=Debug /p:Platform=x64 /t:NavGenerator
```

- `ServerCore` (`Server/ServerCore/ServerCore.vcxproj`) — 게임과 무관한 서버 기반을 담은 **정적 라이브러리**(Network/Job/DB/Utils). `GameServer`가 ProjectReference로 링크하므로 따로 빌드할 필요는 없습니다.
- `GameServer` (`Server/Server/Server.vcxproj`) — 실제 게임 서버, 진입점은 `gameserver.cpp`. 실행은 작업 폴더를 `Server/Server`로 두고 합니다(`Resource/`·DataTable 상대 경로). MSBuild로 프로젝트만 빌드할 때는 `/p:SolutionDir=<Server 폴더>\`를 넘깁니다.
- `BotEngine` (`Server/BotEngine/`, 정적 라이브러리) — LoadTest와 DummyClient가 공유하는 봇 엔진. 논블로킹 소켓 + WSAPoll 워커 스레드로 봇 N명을 램프업 접속시켜 가입/로그인 → 입장 → 이동·사냥(hunt)·핑을 돌리고 지연·처리량을 집계합니다(`GConfig`/`GStat`, `BotEngine::Start/UpdateRamp/TakeSamples/GetSnapshot/Stop`, `ServerProcSampler`). 봇은 클라이언트 측이라 ServerCore를 쓰지 않습니다(DECISIONS 2026-10-30). 프로토콜은 `Server/Server/Protocol/`의 생성 코드를 직접 컴파일하므로 `GanPackets.bat` 뒤에 따로 복사할 것이 없습니다. 새 패킷을 봇이 보내거나 받아야 하면 `BotEngine.cpp`의 `HandlePacket`/`WorkerMain`에 추가합니다.
- `LoadTest` (`Server/LoadTest/`) — BotEngine의 헤드리스 콘솔 프런트엔드. `--bots --ramp-rate --duration` 등 런타임 인자로 동작하고 지연(RTT)·처리량·서버 CPU를 CSV로 기록합니다. 수치 검증용. 사용법은 [Docs/TESTING.md](../Docs/TESTING.md) 참고.
- `DummyClient` (`Server/DummyClient/`) — BotEngine의 OpenGL 시각화 프런트엔드(시연용). LoadTest와 같은 인자로 봇을 돌리고 탑다운 화면에 봇·몬스터·스폰·통계를 그립니다(`GConfig.trackWorld`로 엔진이 몬스터 이동·사망과 스냅숏을 추가로 추적). 창을 닫을 때까지 실행. 사용법은 [Docs/TESTING.md](../Docs/TESTING.md) 참고.
- `NavGenerator` (`Server/NavGenerator/`) — Recast/Detour 내비메시 데이터를 오프라인으로 생성하는 도구. 사용법: `NavGenerator.exe <GeoBinPath> <NavOutputPath>` (인자를 생략하면 기본 맵 `ParagonSample`을 사용해 `../MapResource/Export/<맵>/Geometry/<맵>_Geo.bin`을 읽어 `../Server/Resource/Map/<맵>_Geo.nav`로 출력). **UE에서 맵 지오메트리를 다시 export할 때마다 재실행해야 합니다.** 가장 넓은 연결 영역만 걷기 가능으로 남기고 나머지 섬(능선 꼭대기, 바위·건물 윗면)은 폴리곤 flags를 0으로 꺼서 서버 질의에서 빠지게 합니다(2026-11-17, 출력의 `[Prune]` 줄). 폴리곤 메시 정점이 단일 타일 상한(65,534)을 넘으면 실패로 끝납니다. 검증용으로 `NavMesh_Output.obj`와 무작위 표본 `NavMesh_Samples.csv`(UE 좌표)를 작업 폴더에 씁니다. **검증용 질의 모드**(L2e, `NavQuery.cpp`): `NavGenerator.exe --query <nav 파일> <질의 파일>` — 서버 `NavmeshManager`와 같은 질의(탐색 범위·노드 2,048개·경로 폴리곤 256개)를 `.nav`에 대고 실행해 CSV로 출력합니다(UE 좌표, 한 줄에 질의 하나: `near`(가장 가까운 걷는 점·높이) / `path`(경로가 끝까지 닿는지·폴리곤 수·부분 결과·노드 부족) / `route`(path + 꺾임점) / `move`(`CanMove`와 같은 판정)). 맵을 다시 내보낸 뒤 마커가 걷는 영역 위인지, 먼 경로가 상한 안에서 끝나는지 이것으로 점검합니다. **`NavmeshManager::CanMove`를 고치면 `NavQuery.cpp`의 `move`도 같이 고칩니다**(두 프로젝트가 코드를 공유하지 않음). 런타임에는 `NavmeshManager`가 이 출력을 사용합니다. 지오메트리는 `Server/MapResource/MapExport.bat <맵>`(UE 커맨드렛 `MapExportCommandlet` → NavGenerator)으로 만들며, **UE에서 캐릭터가 부딪히는 메시와 지형(스태틱메시·ISM·Landscape, 충돌 켜짐 + Pawn Block)만** Detour 좌표(UE (x,y,z) → (y,z,-x), 정점 순서 반대)로 내보냅니다 — 서버 이동 검증이 이 내비메시를 쓰므로 기준이 어긋나면 지나갈 수 있는 곳에서 플레이어가 끌려갑니다(2026-10-30 S1). 이 환경에서는 bat을 전체 경로로 실행합니다.

서드파티 라이브러리(Recast/Detour, Protobuf, ODBC용 `sql.h`/`sqlext.h`)는 `Server/ThirdParty/`에 있습니다. 서버에는 자동화된 테스트 스위트가 없습니다 — 검증은 `GameServer`를 빌드해서 `LoadTest`/`DummyClient`나 UE 클라이언트로 붙여보는 방식으로 합니다.

프로토콜(생성된 `.pb.h`/`.pb.cc`)은 `Server/Server/Protocol/`에 복사되어 들어옵니다. 이 파일들은 [Common/Protocol/CLAUDE.md](../Common/Protocol/CLAUDE.md)에서 관리하며, 절대 손으로 수정하지 마세요.

## 서버 아키텍처

서버는 단일 프로세스 · 멀티스레드 IOCP 서버이며, 다음 흐름으로 구성됩니다: 네트워크 I/O → 커넥션별 `Session`(게임 쪽은 `GameSession`) → `PacketHandler` → 게임 로직이 오너별 `JobQueue` 위의 `Job`으로 디스패치됨.

**계층과 폴더 (2026-10-30 C-5)** — 의존은 GameServer → ServerCore 한 방향입니다.
- `ServerCore/` (정적 라이브러리, 미리 컴파일 헤더 `CorePch.h`): `Network/`(IocpCore, IocpEvent, Listener, NetAddress, ServerService, Session, SendBuffer, RecvBuffer, NetStats) · `Job/`(Job, JobQueue, Timer) · `DB/`(DBConnection, DBConnectionPool) · `Utils/`(RWLock, ConcurrentQueue, CsvFile, CoreUtils). **ServerCore는 Protocol·게임 헤더를 include하지 않습니다.** 게임이 필요하면 가상 훅(`Session::OnConnected/OnDisconnected/OnRecvPacket`)이나 주입(`ServerService`의 `SessionFactory`)으로 연결합니다.
- `Server/` (GameServer, `pch.h` = `CorePch.h` + Protocol + 게임 공용 헤더): `Session/`(GameSession) · `Packet/`(PacketHandler, PacketSerializer) · `DB/`(DatabaseWorker) · `Data/`(ServerData) · `Game/Object/`(GameObject, Character, Player, Monster, DropItem, StatComponent) · `Game/Item/`(Inventory) · `Game/Combat/`(CombatProcessor) · `Game/Room/`(Room, RoomManager) · `Game/World/`(GameMap, NavmeshManager) · `Game/Lobby/`(AuthLobby) · `Utils/`(MathUtils, Metrics) · `Protocol/`(생성 코드) · `Resource/`.
- `#include`는 프로젝트 루트 기준 경로로 씁니다(`"Network/Session.h"`, `"Game/Room/Room.h"`). GameServer의 include 경로는 `$(ProjectDir)`와 `$(SolutionDir)ServerCore`이므로 **두 프로젝트에 같은 파일 이름을 만들지 않습니다.** 새 파일은 vcxproj와 `.filters`에 같은 폴더로 추가합니다.

- **IOCP 코어** (`IocpCore`, `IocpEvent`, `Listener`, `ServerService`): accept/recv/send 완료 루프를 직접 처리합니다. `gameserver.cpp`의 `worker_thread`는 `IocpCore::Dispatch()`를 반복 호출할 뿐이며, 네트워크 스레드 자체에는 로직이 없습니다.
- **Job/JobQueue 패턴** (`Job.h`, `JobQueue.h`): 서버의 동시성 모델입니다. 여러 IOCP 워커 스레드에서 안전하게 접근해야 하는 객체(실제로는 `Room`)는 `JobQueue`를 소유하고, 그 큐에서 실행되는 `Job` 안에서만 자기 상태를 변경합니다(`Room::PushJob` / `Room::ReserveJob`). `JobQueue` 자체도 `IocpObject`라서, Job을 push하면 완료 이벤트가 포스트되어 IOCP 워커 스레드가 이를 집어서 처리합니다(`ExecuteJobs`). **`Room`의 내부 상태는 절대 Job 밖에서 직접 건드리지 말고 반드시 `PushJob`/`ReserveJob`을 통해야 합니다.**
- **세션 & 패킷**: `Session`(코어)이 `RecvBuffer`/`SendBuffer`와 패킷 경계(`PacketHeader`, `MAX_PACKET_SIZE`)를 처리하고, 패킷 하나마다 `OnRecvPacket`을 부릅니다. `GameSession`이 `_currPlayer`를 갖고 `PacketHandler::ProcessPacket`으로 넘기며, 접속이 끊기면 `OnDisconnected`에서 방 퇴장 Job을 넣습니다. `PacketHandler::ProcessPacket`이 원시 바이트를 `PacketId`(`Common/Protocol/Enum.proto` 참고)로 구분되는 Protobuf 메시지로 파싱하고, `GPacketHandler` 테이블을 통해 `Handle_CS_*` 함수로 디스패치합니다.
- **월드 모델**: `RoomManager`가 하나 이상의 `Room`을 소유합니다(현재는 시작 시 단일 룸만 생성). 각 `Room`은 자신의 `GameMap`(시야(AOI): `AoiIndex` = 큰 셀 + 셀마다 쿼드트리, 시야는 거리로 판정 — 들어옴 ≤ R, 나감 > R+H(히스테리시스). `GameMap::EnterMap/UpdateMap/LeaveMap`이 주체의 `_viewList`와 비교해 `ViewUpdate`를 만들고 `Room::UpdateView`가 양쪽 목록·ADD/REMOVE에 반영, `BroadcastAOI`는 `_viewList`로 전송. 수치는 `WorldTable.csv`(셀 50m, 분할 8명, 최소 노드 5m, R 50m, H 5m), 레벨 이름은 `ServerConfig` `[World] MapName`(`GServerConfig.mapName`), Room 정원은 `WorldTable.RoomCapacity`(`Room::_capacity`). **위치를 바꾸면 이동이 끝난 뒤 반드시 `UpdateMap`(플레이어 `PlayerMove`, 몬스터 `NPCMove`)을 불러야 한다** — 늦게 부르면 AOI가 옛 위치를 들고 경계에서 판정이 틀린다(`[Debug] ViewAudit`로 확인))과 자신의 `NavmeshManager`(이동 검증 및 몬스터 경로탐색용 Recast/Detour 내비메시, `NavGenerator`로 오프라인 생성)를 각각 소유합니다.
- **엔티티**: `GameObject` → `Character` → `Player` / `Monster`. 전투 판정은 `CombatProcessor`와 `Room::CharacterAttack` / `ExecuteSkillHit` / `ApplyDelayedDamage`를 거치며, 스킬/캐릭터/아이템 밸런스 데이터는 `DataManager`(`ServerData.h`/`.cpp`)가 `Common/DataTable/PlayerStatTable.csv`(플레이어 레벨별 기본 스탯, 체형 공용), `SkillTable.csv`, `MonsterTable.csv`(몬스터 종류별 스탯·스킬 — ID는 `ObjectInfo.template_id`), `ItemTable.csv` 등을 읽어 제공합니다(`CsvFile`이 파서). 시전할 스킬은 `Character::GetSlotSkill`(순수 가상)이 정합니다 — `Player`는 무기 타입 + 슬롯, `Monster`는 `MonsterTable.SkillId`.
- **영속성(Persistence)**: `DBConnection`/`DBConnectionPool`/`DatabaseWorker`가 raw ODBC(`sql.h`/`sqlext.h`) 호출로 SQL Server를 래핑합니다. `DatabaseWorker`는 IOCP 스레드를 막지 않도록 전용 큐에서 DB 작업을 비동기로 처리합니다. 연결 문자열은 `ServerConfig.ini`의 `[Database] ConnectionString`(기본 `Driver={ODBC Driver 17 for SQL Server};Server=.\SQLEXPRESS;Database=GameServer;Trusted_Connection=Yes;`)에서 읽습니다 — Windows 통합 인증이라 비밀번호는 없고, 비밀번호가 필요한 DB는 파일 대신 환경변수 `JH_DB_CONNECTION`으로 줍니다(아래 "서버 설정"). 로컬에서 서버를 실행하려면 SQL Server Express(기본 인스턴스명 `SQLEXPRESS`)와 ODBC Driver 17이 설치돼 있고 `GameServer` DB가 있어야 합니다. 테이블: `User_Account`, `User_Info`, `Player_Info`, `Player_Item`, `Schema_Version`.
- **DB 스키마·SQL 관리 (A2.5, D-150)**: 스키마는 `Server/Resource/DB/`에서 관리합니다. `schema.sql` = 새 DB 생성용(최신 버전 행까지 포함), `migrations/NNNN_<날짜>_<내용>.sql` = 기존 DB를 바꾸는 변경(4자리 순번, 한 트랜잭션, 다시 실행해도 안전하게 `IF NOT EXISTS`, 파일 끝에서 자기 `Schema_Version` 행 INSERT, `USE` 문 없음), `migrate.ps1` = 실행기(`-Status`로 상태만 보기, 기본은 `BACKUP DATABASE` 후 남은 것을 순번대로 적용, `-Server`·`-Database`·`-SkipBackup`). 서버는 마이그레이션을 실행하지 않고, 시작할 때 DB의 `MAX(Schema_Version.Version)`이 `DbQueries::DB_SCHEMA_VERSION`과 다르면 오류를 남기고 시작하지 않습니다(`DatabaseWorker::CheckSchemaVersion`). **테이블·열을 바꿀 때는 마이그레이션 파일 + `schema.sql` + `DB_SCHEMA_VERSION` 증가를 한 커밋에서 함께 합니다.** 서버가 실행하는 SQL 문자열은 전부 `Server/Server/DB/DbQueries.h`에 둡니다(저장 프로시저 없음, `DatabaseWorker`는 바인딩·실행·결과 전달만). 값은 `?` 파라미터로 넘기고 쿼리에 직접 넣는 것은 서버가 검증한 정수뿐입니다.
- **플레이어 저장 (A2.5, D-151)**: 저장은 Room 잡에서 요청하고 `DatabaseWorker`가 실행한 뒤 결과를 Room 잡으로 돌려줍니다. 진행 상황(`Player::progressSave`, 레벨·경험치·HP, `Room::RequestProgressSave`)은 `Player::SaveState`(플레이어당 동시 1건, 진행 중 요청은 합침)로 관리하고, `Player::MakeProgressSnapshot()`이 만든 `DB_PlayerProgress`를 `lastSavedProgress`(DB에 있는 값)와 비교해 **다를 때만** 저장하므로 값을 바꾸는 코드에 변경 표시를 넣지 않습니다. 저장 시점은 주기(`Room::UpdateSaves`, `ServerConfig` `PlayerSaveIntervalSec`)와 방 퇴장이고, 더미 봇(`isDummy`, 전원이 한 행)은 저장하지 않습니다. 저장할 필드를 늘리려면 `DB_PlayerProgress`·`MakeProgressSnapshot`·`DbQueries::UpdatePlayerProgress`·`DatabaseWorker::SavePlayerProgress` 바인딩을 함께 고칩니다. **아이템·골드는 이 스냅숏에 넣지 않습니다**(아래 "아이템 작업"). 로그인(`Player::InitFromDb`)은 DB 레벨로 `PlayerStatTable`을 조회하고(행이 없으면 로그인 거부) HP는 DB 값을 장비 반영 최대치 안으로 맞춥니다(저장 이력이 없으면 최대치, 0 이하면 부활 규칙 값).
- **아이템 작업 (A3.3, D-153·D-165, 설계 [Docs/DESIGN_ITEMS_TRADE.md](../Docs/DESIGN_ITEMS_TRADE.md))**: 아이템 한 개(스택 한 묶음) = `Player_Item` 한 행(`ItemDbId`), 메모리 사본은 `Player::inventory`(`Game/Item/Inventory`, 인벤토리 + 장착)이고 **권위는 DB**입니다. 아이템·골드의 소유가 바뀌는 동작은 모두 ① Room 잡에서 검증하고 계획(`DB_ItemOp`)을 채움 → ② `Room::StartItemOp`가 `Player::itemOp.inFlight`를 켜고 `DatabaseWorker::ExecItemOp`로 보냄(한 트랜잭션) → ③ `Room::OnItemOpDone`이 성공일 때만 메모리·패킷(`SC_INVENTORY_UPDATE`, 장착이면 `SC_CHANGE_EQUIP` 방송)에 반영하는 순서입니다. 플레이어당 동시에 1건이고 진행 중에 온 요청은 쌓지 않고 `BUSY`로 거부합니다(`Room::CheckItemRequest`, 장착은 `PlayerChangeEquip` 안에서). 결과가 왔을 때 플레이어가 방에 없으면 반영만 건너뜁니다(DB에는 이미 들어갔고 다음 로그인 때 읽음). 골드는 `Gold = Gold + ?`로 증감하고 돌려받은 잔액을 `Player::SetGold`로 넣습니다(메모리에서 더하지 않음, `UpdatedAt`은 건드리지 않음 — NULL이면 "저장한 적 없음"으로 로그인 HP 판단에 씀). SQL은 `DbQueries.h`의 공통 틀(`ItemOpHead`/`ItemOpTail`: TRY 안에서 `BEGIN TRAN` → 문장마다 바뀐 행 수 누적 → 기대와 다르면 롤백, 결과 집합 하나 `Ok, Kind, V`)을 쓰고, **성공 상태 행을 읽었을 때만 성공**으로 봅니다(`DBConnection::Execute`는 배치 첫 문장의 성공만 알려 줌). 모든 UPDATE는 기대 상태(`OwnerId`·`Location`·`EquipSlot`·`Count`)를 WHERE에 적습니다. 자주 쓰는 작업(장착)은 파라미터가 고정된 쿼리(`ItemEquip`), 드문 작업(개발 지급 `BuildItemGive`, 로그인 보정 `BuildItemLoginFix`)은 검증된 정수를 넣어 조립합니다 — 조립식은 요청마다 컴파일이라 DB 실행이 약 5배 느립니다(`TESTING.md` A3.3). 실패는 "롤백 확인(결과 행 `Ok` 0 — `DB_ERROR`만 알림)"과 "불명(실행 오류·결과 행 없음 — DB에 반영됐을 수 있어 접속을 끊고 재로그인으로 다시 읽게 함, `DB_ItemOpResult.unknown`)"으로 나눕니다. 트랜잭션은 `SET LOCK_TIMEOUT 5000`으로 시작합니다(연결에 남는 설정). **새 아이템 작업을 추가할 때**: `ItemOpKind` + `DB_ItemOp` 필드 + `DbQueries` 쿼리 + `ExecItemOp`의 분기 + `OnItemOpDone`의 분기를 함께 넣고, 요청 핸들러는 `CheckItemRequest` → 검증 → `StartItemOp` 순서를 지킵니다. **인벤토리 칸(A6.1, D-166)**: 인벤토리 행은 칸 번호 `BagSlot`(0부터, 그 밖의 위치는 -1, 유니크 인덱스 `UX_Player_Item_BagSlot`)을 갖고 메모리에서는 `ItemInstance::slot`입니다. 인벤토리로 들어오는 행을 만드는 작업은 `Inventory::FreeSlots`로 빈 칸을 골라 계획에 넣고(`PlanAdd`의 `newSlots`, 장착의 `oldSlot`·`offhandSlot`), 인벤토리 밖으로 내보내는 작업은 `BagSlot`을 -1로 함께 바꿉니다. 칸 수 상한은 "빈 칸이 없으면 거부"로 지킵니다. 칸 옮기기·맞바꾸기는 `CS_MOVE_ITEM` → `Room::PlayerMoveItem` → `ItemOpKind::Move`(`DbQueries::ItemMove`). 장착(`ItemEquip`)과 칸 맞바꿈은 UPDATE 한 문장입니다 — 유니크 인덱스는 문장 끝에 검사하므로 맞바꿈이 중간 상태 없이 되고, 두 문장으로 나누면 어느 순서든 한쪽 인덱스를 어깁니다. ItemTable에 없어 메모리에 올리지 않은 행의 칸은 `Inventory::ReserveSlot`으로 비워 둡니다. `Player_Item`에는 필터 유니크 인덱스(`UX_Player_Item_Equip`·`UX_Player_Item_BagSlot`)가 있어 `QUOTED_IDENTIFIER`·`ANSI_NULLS`가 켜진 연결에서만 쓸 수 있습니다(서버 ODBC·`migrate.ps1`은 켜져 있음, `sqlcmd`로 직접 고칠 때는 `-I`). 지표는 `[metrics] itemOp(sent/fail/busy inflight)`·`itemOpMs`·`equipApplyMs`(장착 요청 → 적용, 기준 p99 50ms — D-163).
- **장착 (MC3.2·A3.3, D-156)**: `CS_CHANGE_EQUIP(part, item_db_id)`(0 = 해제) → `Room::PlayerChangeEquip`이 슬롯·보유(내 인벤토리 위치의 행)·아이템 슬롯·방패는 한손검·사망·시전·`RequiredLevel`·빈도·진행 중인 작업·빈 칸을 검증하고 `ItemOpKind::Equip`을 보냅니다. 옛 장비와 자동 해제되는 방패(무기가 한손검이 아니게 될 때)를 같은 트랜잭션에서 내립니다. 메모리 반영(`Inventory`·`SetEquippedItem`·`RecalcStat`·무기 스왑 잠금)과 방송(보조손 해제 먼저)은 결과 적용 시점이며, 그때는 사망·시전을 다시 보지 않습니다(이미 DB에 반영됨). 그래서 무기 슬롯 작업이 DB에 가 있는 동안(`itemOp.weaponSwapPending`)에는 `Room::CastSkill`이 그 플레이어의 시전을 받지 않습니다(받으면 스왑 잠금이 시전의 행동 잠금을 덮어써 짧아짐). 로그인 때 맞지 않는 장착 행(슬롯 불일치, 검이 아닌데 방패)은 `InitFromDb`가 메모리에서 인벤토리로 내리고 `pendingEquipFix`에 적어 두면 `PlayerEnterRoom`이 `LoginFix` 작업으로 DB도 고칩니다. 더미 봇은 장착·아이템 요청이 모두 `NOT_ALLOWED`이고 `SC_INVENTORY`도 받지 않습니다(D-161·D-164).
- **바닥 드랍 (A3.4, D-157, 설계 [Docs/DESIGN_ITEMS_TRADE.md](../Docs/DESIGN_ITEMS_TRADE.md) "A3.4 구현 메모")**: 몬스터가 죽으면 `Monster::OnDead` → `Room::SpawnMonsterDrops`가 `DataManager::RollDrops`를 굴려 걸린 행마다 `DropItem`(`Game/Object/DropItem.h`, `OBJECT_TYPE_ITEM`, `template_id` = itemId·0은 골드, `ObjectInfo.item_count` = 수량)을 사망 지점 `DropScatterCm` 안에 만듭니다(`Room::CreateDrop`). 드랍은 `Room::_drops`에만 있고 **`_objects`에는 넣지 않습니다**(`_objects`는 캐릭터 전용 — 전투·시야 코드가 `Character`로 바로 캐스팅함). id는 방마다 1,000,000,000부터. 소유권은 막타가 개별 계정 플레이어일 때 `ownerUID`·`ownerUntilMs`(`DropOwnerSec`)로 적고 줍기 때 `DropItem::CanPickup`으로 판정합니다(더미 봇·공격자 없음은 소유권 없음). 시야는 캐릭터와 분리: `GameMap::_dropAoi` + `Player::dropView`, `Room::UpdateDropView`(입장·`PlayerMove`·`PlayerRevive`)·`CreateDrop`·`RemoveDrop`이 `SC_ADD_OBJECT`/`SC_REMOVE_OBJECT`를 보냅니다 — **플레이어 위치를 바꾸는 경로를 추가하면 `UpdateMap` 뒤에 `UpdateDropView`도 부릅니다.** 소멸은 `ReserveJob(DropLifeSec)` → `Room::ExpireDrop`(id로 다시 찾고 `expireAtMs`·`picking` 확인), `MaxDropsPerRoom`을 넘으면 만든 순서대로 지웁니다. 지표 `[metrics] drops(now kills/created/expired/evicted)`, Debug 로그 `[Drop] 생성`.

## 네이밍 컨벤션

Server 코드는 별도 접두사 규칙 없이 기능 위주로 클래스/함수명을 짓습니다. 전역 싱글턴에 `G` 접두사를 붙이는 것이 유일한 고정 관례입니다 (`GRoomManager`, `GTimer`, `GDBWorker`, `GLobby`).

## 알려진 함정 (Gotcha)

세션 중 발견한, 놓치기 쉬운 규칙을 여기에 누적합니다.

- `Room`의 내부 상태는 절대 `PushJob`/`ReserveJob` 밖에서 직접 변경하지 마세요 — 여러 IOCP 워커 스레드가 동시에 접근하는 객체이므로 레이스 컨디션이 발생합니다.
- 플레이어 이동은 `Room::PlayerMove`가 검증합니다(서버 권위 이동, S1 — [Docs/DESIGN_CONTROL_CAMERA.md](../Docs/DESIGN_CONTROL_CAMERA.md)). 보정은 `Player::moveGuard.correctionSeq`를 올리고 본인에게만 `SC_MOVE_OBJECT`를 보내며, 순번이 다른 이동은 버립니다. 검증 허용치는 `MovementTable`의 `Server*` 열, 속도는 스탯 `MoveSpeed`(플레이어 `PlayerStatTable`)입니다. 지형 검사(`NavmeshManager::CanMove`)는 ① 직선 레이캐스트가 끝까지 가거나 막힌 점이 목표에서 `ServerNavToleranceCm` 안이면 통과 ② 막혔어도 목표가 걷는 영역에서 허용치 안이고 걷는 영역 위로 돌아가는 길이 ≤ 이동 거리 + 허용치 × 2이면 통과(L2e, D-186 — 내비메시 경계가 충돌 도형에서 20~55cm 밖이라 장애물에 붙어 도는 캐릭터는 시작점·목표가 모두 경계 밖일 수 있음. 폭 약 60cm 이하 물체는 통과를 막지 못함). 이동 높이 z는 클라이언트 값을 그대로 저장합니다(3m 넘게 어긋난 z를 받으면 이후 이동이 모두 거부됨 — 백로그). 결과는 `[metrics]`의 `move(total ok/speed/nav/bad/stale/rate)`로 봅니다.

## 서버 설정 (ServerConfig.ini)

운영 값(포트, 바인드 IP, 띄울 레벨 `[World] MapName`(맵 리소스 파일 이름 = `WorldTable.MapName`, 코드 기본값 `ParagonSample`·`ServerConfig.ini` 값 `Continent01`. 로그인 성공 응답 `SC_LOGIN_INFO_PACKET.map_name`으로 클라이언트에 알려 주고 클라이언트는 그 레벨을 엶 — D-185), IOCP 워커 수, 중복 접속 대기·강제 제거 시간 `LoginWaitTimeoutSec`·`LoginCloseForceSec`, DB 연결 문자열·연결 수·진행 상황 주기 저장 간격 `PlayerSaveIntervalSec`, 로그 레벨·폴더)은 `Data/ServerConfig`(`GServerConfig`)가 시작할 때 읽습니다. 게임 수치는 여기 두지 않고 DataTable에 둡니다. 우선순위(뒤가 앞을 덮어씀): 코드 기본값 → `Server/Server/ServerConfig.ini`(커밋) → 같은 폴더의 `ServerConfig.local.ini`(있으면, 커밋하지 않음) → 환경변수 `JH_DB_CONNECTION` → 명령줄 `--config <경로>`·`--port <n>`. 시험용 `--roll-drops <횟수>`는 DataTable만 읽고 드랍 롤 빈도를 로그에 남긴 뒤 종료합니다(DB·포트를 열지 않음, 잘못된 CSV 시험에도 씀). 설정 파일이 없거나 모르는 키·잘못된 값이 있으면 줄 번호와 이유를 출력하고 시작을 중단합니다. 시작 로그의 `[Config]` 줄에 적용된 값과 출처가 찍힙니다(`PWD`는 가림). 다른 PC에서 봇을 붙이려면 `BindIp=0.0.0.0`. 부하 시험용 `[Debug]`: `DummySpawnZone=x,y,r[,n];...`(더미 봇 로그인을 들어오는 순서대로 앞 구역부터 n명씩 원 안에 배치 = 핫존·시야 경계 시험, 비우면 맵 전체 무작위), `ViewAudit=true`(방마다 1초에 한 번 플레이어 시야 목록을 실제 거리와 비교 — 거리 ≤ `WorldTable.ViewRadiusCm`인데 없으면 누락, > R+`ViewHysteresisCm`인데 있으면 초과, `[metrics] viewAudit(must/missing mustNot/extra)` 누적과 처음 10건 WARN 로그. 전수 검사라 부하 측정 때는 끈다), `DbSaveDelayMs=<ms>`(아이템 트랜잭션·진행 상황 저장 실행 전에 멈춤 — 빠른 재접속·중복 접속·결과 도착 전 접속 해제 시험용, DB 작업 스레드를 막으므로 평소에는 0), `DevCommands=true`(개발 지급 명령 `CS_DEV_GIVE`를 받음), `DbItemFailEvery=<n>`(아이템 트랜잭션을 n번에 한 번 일부러 롤백 — DB 실패 때 메모리·DB가 그대로인지 시험, D-162). 새 키는 `ServerConfig.cpp`의 `ApplyFile`과 `Print`에 추가하고 `ServerConfig.ini`에도 적습니다. INI 파서는 ServerCore `Utils/ConfigFile`(값 뒤 주석은 지원하지 않음).

시작 순서 주의: 시작 실패 시 `exit()`가 전역 소멸자에서 끝나지 않는 스레드(`GTimer`, DB 작업 스레드)를 join하며 멈추므로, 실패할 수 있는 단계(설정 → DataTable → 포트 → DB 연결)를 스레드를 만드는 단계보다 먼저 둡니다.

## 로그 (Logger)

서버 출력은 `cout`/`printf` 대신 ServerCore `Utils/Logger`의 `LOG_DEBUG/INFO/WARN/ERROR("카테고리", "형식 {}", 값)`(std::format 문법)을 씁니다. `CorePch.h`에 들어 있어 어디서나 쓸 수 있습니다. 게임 스레드는 레벨 확인 → 포맷 → 큐에 넣기만 하고 전용 스레드가 콘솔과 `Log.Dir`(기본 `Server/Server/Logs/GameServer_<시작시각>.log`, 커밋 안 됨)에 씁니다. 큐가 가득 차면(65,536줄) 버리고 개수를 세며(`[metrics]`의 `logDrop`, `[Logger]` 경고 줄), 종료(`exit`·Ctrl+C·창 닫기) 시 남은 로그를 씁니다. 레벨 기준: 플레이어·연결·패킷마다 남는 로그는 **Debug**(기본 Info에서는 출력 안 됨), 시작·로드·메트릭은 Info, 비정상 입력은 Warn, 실패는 Error. 와이드 문자열은 `Utils::WStringToUTF8`로 바꿔 넘깁니다.

**인코딩:** 서버 프로젝트(GameServer·ServerCore·NavGenerator·봇)는 모두 `/utf-8`로 컴파일하고 소스는 UTF-8입니다. 문자열 리터럴·로그 파일·콘솔·클라이언트 문자열(Protobuf)이 모두 UTF-8이므로, 클라이언트 문자열을 `WCHAR`로 바꿀 때는 `CP_UTF8`(또는 `Utils::UTF8ToWString`)을 씁니다(`CP_ACP` 금지).

## 데이터 테이블 (CSV 로더)

서버는 시작할 때 `Common/DataTable/*.csv`를 읽어 스탯/스킬/몬스터/아이템/드랍(`DropTable`)/경제(`EconomyTable`)/이동 검증/시야(AOI) 수치를 로드합니다(규약·컬럼: [Docs/DESIGN_DATA.md](../Docs/DESIGN_DATA.md)). 애셋 참조 컬럼은 서버가 무시합니다. CSV 형식 오류·중복 키·없는 참조가 있으면 서버가 시작을 중단하며, 폴더는 환경변수 `JH_DATA_DIR` 또는 `../../Common/DataTable`에서 찾습니다. 새 테이블은 `DataManager::Init()`에 같은 방식으로 추가합니다.
