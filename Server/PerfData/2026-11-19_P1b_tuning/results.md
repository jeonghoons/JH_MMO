**상태: T를 아직 정하지 못했습니다.** 밀집은 목표에 들어오지만, 분산 1,000이 수정 전보다 나빠졌고 실제로 모이는 시간이 설정값 T를 따르지 않습니다. 원인 조사가 먼저입니다(맨 아래 "다음에 할 일").

## 환경
- PC i5-10400F, 서버·봇 같은 PC, Release x64, 에디터 닫음. 빌드: 작업 트리(P1b 구현 + 동시성 리뷰 반영, 커밋 전) + 직전 커밋 `c7b74a0`.
- 레벨 `Continent01`, `RoomCapacity` 100, 워커 6(기본). 봇 인자·집계 방법은 P1a 기준선(`../2026-11-19_P1a_baseline/results.md`)과 같음. 핫존 = 마을 광장 `-14200,0,1000`.
- 실행 이름 끝의 `tNN` = `SendFlushIntervalMs`(ms). **조합마다 1회만** 잰 값이라 흔들림을 감안해야 합니다.
- 방식(D-206): 세션별 송신 빈도 제한 — 마지막 송신 뒤 T ms가 지난 세션만 보냄, 예외 없이 전부 묶음.

## 읽은 것
- **밀집은 효과가 큽니다.** 핫존 100은 T=10~30에서 핑 38~48ms·틱 지연 10~14ms·CPU 18~25%로 목표(핑 ≤ 50, 틱 지연 ≤ 20, CPU ≤ 25%, 호출당 ≥ 10) 범위입니다. 핫존 50도 초과(52~59ms)에서 통과(19~36ms)로 바뀌었습니다.
- **T=0은 묶이지 않습니다**(호출당 1.00, 수정 전과 같음). 계산과 같습니다.
- **문제 1 — 모이는 시간이 T를 따르지 않습니다.** 핫존 100의 세션당 호출 수로 역산한 실제 주기: T=5 → 약 20ms, T=10 → 약 53ms, T=20 → 약 39ms, T=30 → 약 40ms. T=10이 T=20보다 길게 모이는 등 순서도 맞지 않습니다. 원인 미확인(의심: Timer 스레드의 Windows 타이머 해상도 15.6ms, 봇 이동 패킷이 몰려서 도착).
- **문제 2 — 분산 1,000이 수정 전보다 나빠졌습니다.** 핑 p99 19 → 32~44ms, 틱 지연 p99 14 → 19~24ms(T=5·10은 합격선 20 초과), 서버 CPU 약 1.2~1.5배. "한산한 곳은 지금과 같다"는 예상이 맞지 않았습니다. 원인 미확인(의심: 한가한 방에서 T 안에 온 패킷이 깨우기 타이머를 기다리며 최대 약 15ms 더 늦어짐 — 동시성 리뷰 L2, 깨우기 작업·재포스트의 추가 비용).
- 핫존 25도 T=20에서 핑 11~20 → 34ms로 늘었습니다(T=5·10은 18ms).
- 14회 모두 접속 실패·예상 밖 종료 0, 서버 WARN·ERROR 0.

## 다음에 할 일
1. 원인 조사: (a) 깨우기 타이머가 실제로 몇 ms 뒤에 도는지, (b) 분산 1,000에서 깨우기 작업·재포스트 횟수와 CPU 증가의 관계, (c) 봇 이동 패킷의 도착 간격 분포.
2. 조사 결과에 따라 후보: 타이머 해상도 올리기(`timeBeginPeriod(1)` 또는 고해상도 타이머), 한가한 방에서는 깨우기를 기다리지 않고 바로 보내기(밀려 있을 때만 모음), 송신 완료 직후 재전송의 간격 우회 막기(리뷰 L3).
3. 고친 뒤 이 폴더의 스크립트로 조합마다 2회 이상 다시 재고 T 확정 → 전체 매트릭스(`_P1b_after`) → chaos 램프 → `NetMoveStats` 전/후 + 사용자 PIE.
