# P1b 송신 묶기 — 1차 측정에서 나온 두 문제의 원인 조사 (2026-11-19)

1차 측정(`../2026-11-19_P1b_tuning/results.md`)의 두 문제 — ① 모이는 시간이 T를 따르지 않음 ② 분산 1,000이 수정 전보다 나빠짐 — 의 원인을 찾고 고친 기록입니다. T 고르기는 `../2026-11-19_P1b_tuning2/`에서 이어집니다.

## 환경
- PC i5-10400F, 서버·봇 같은 PC, Release x64, 에디터 닫음. 레벨 `Continent01`, `RoomCapacity` 100, 워커 6(기본). 봇 인자는 P1a 기준선과 같음. 핫존 = `-14200,0,1000`.
- 전부 T(`SendFlushIntervalMs`) = 10ms, 조합마다 2회. 실행 이름: `<시나리오>_t10_<꼬리표>_r<회차>`.
- **이날 오후의 PC 상태는 오전(P1a 기준선)과 달랐습니다.** P1b 전 exe(커밋 `c7b74a0`을 따로 빌드)를 같은 시간대에 다시 재니 분산 1,000의 서버 CPU가 140~143(오전 88~102)이었습니다. 그래서 "수정 전"은 오전 값이 아니라 아래 `pre` 실행과 비교합니다.

## 원인

1. **깨우기 타이머가 늦게 깸(Windows 타이머 해상도 약 15.6ms).** `Timer::Run`의 `wait_until`이 시스템 타이머 단위로만 깨어, 송신 깨우기 작업이 예약 시각보다 평균 3.5~6ms, p99 약 14ms 늦었습니다. 방 틱(100ms 예약)도 같은 이유로 p50 5~6ms 늦었습니다.
2. **내보내기가 방 스레드를 막음.** `WSASend` 1회가 44~73µs라 핫존 100에서 세션 약 100개를 한 번에 내보내면 방 스레드가 7~10ms 멈추고(`flushRunMax`), 그동안 들어온 작업이 밀렸습니다(작업 큐 대기 p50 8~17ms, p99 35~47ms — 작업 자체는 0.4ms). T=10이면 붐빌 때 방 스레드의 약 70%가 내보내기였습니다. 1차 측정에서 "T와 무관하게 40~50ms씩 모인" 이유입니다.
3. **송신 완료 직후 재전송이 송신 간격을 건너뜀.** 2번을 고쳐 방 스레드가 안 막히자, 송신 중에 쌓인 메시지를 `ProcessSend`가 완료 즉시 다시 보내 묶임이 절반으로 줄었습니다(초당 5~12회 → 약 2,500회).
4. 작업이 몰려서 도착하는 것(방 스레드 진입 초당 80~90번에 작업 600개)은 봇의 폴 주기·서버 틱이 같은 시스템 타이머에 묶여 생기는 것으로 보이며, 1·2를 고친 뒤에는 지표에 문제를 일으키지 않아 손대지 않았습니다.

확인했지만 원인이 아니었던 것: IOCP 포스트 → 실행 지연(p99 0ms), 2ms 독점 상한의 재포스트(초당 40~350회, 틱 지연과 무관), 묶기 자체의 CPU 비용(T=0 대조군이 T=10보다 CPU가 높음).

- 분산 1,000은 회차 간 편차가 큽니다(`kick8c` 핑 p99 16 대 32). 2회로는 수정 사이의 작은 차이를 가를 수 없고, "수정 전보다 나빠지지 않았다"까지만 말할 수 있습니다.
- 이 폴더의 33회 모두 접속 실패·예상 밖 종료 0, 서버 WARN·ERROR 0.

## 채택한 변경
- `[Network] TimerResolutionMs`(기본 1) — 서버 시작 때 `timeBeginPeriod`.
- `JobQueue::FlushDueSends`: 앞 8개(`INLINE_FLUSH_MAX`)는 직접, 나머지는 16개씩(`SEND_BATCH_SIZE`) `SendBatchEvent`로 IOCP 워커에게.
- `Session::ProcessSend`: 잡 큐에 등록된 세션(`_flushPending`)은 완료 직후 재전송하지 않음.
- 계측(`[metrics]`의 `sendPath`·`flushGap`·`sendWake`·`jobs`·`jobWait`·`jobDispatch`·`busy`, `metrics.csv` 열)은 남김.
