# P1b 송신 묶기 뒤 전체 매트릭스 (2026-11-19)

P1a 기준선(`../2026-11-19_P1a_baseline/`)과 같은 시나리오·인자로 P1b 뒤를 쟀습니다. T(`SendFlushIntervalMs`) = 10ms, `TimerResolutionMs` = 1(D-207). 원인 조사는 `../2026-11-19_P1b_cause/`, T 고르기는 `../2026-11-19_P1b_tuning2/`.

## 환경
- PC i5-10400F(6코어 12스레드), 서버·봇 같은 PC, Release x64, 에디터 닫음. 레벨 `Continent01`, `RoomCapacity` 100. 봇 인자는 P1a 기준선과 같음(`--move-interval 200 --threads 4`, 핫존 = 마을 광장 `-14200,0,1000`).
- `after` = 작업 트리 빌드(커밋 전, 직전 커밋 `c7b74a0`). `pre` = P1b 전(커밋 `c7b74a0`을 따로 빌드한 exe).
- **이날 오후는 오전(P1a 기준선)보다 CPU가 높게 나오는 PC 상태였습니다**(분산 1,000 수정 전: 오전 88~102 → 오후 140~158). 그래서 시나리오마다 `pre`와 `after`를 바로 이어서 쟀고(`run_matrix.sh`), 아래 "수정 전"은 오전 값이 아니라 이 `pre`입니다.
- 실행 이름 `<시나리오>_w<워커>_<pre|after>_r<회차>`, 각 2회.

## 판정
- **기존 합격선(D-057)**: `after` 워커 6의 14회 모두 통과. 같은 시간대의 `pre`는 핫존 100·핫존 50·분산 200(2회 모두), hunt 200(1회)이 불합격.
- **P1b 목표**: 핫존 100 핑 p99 ≤ 50 ✔(21~23), 틱 지연 p99 ≤ 20 ✔(10~12), 호출당 메시지 ≥ 10 ✔(14.2~22.7), 분산 1,000 핑 p99 ≤ 40 ✔(24~31, 수정 전 22~29와 같은 범위). **핫존 100 서버 CPU ≤ 25%는 미충족**(26%·42%, 수정 전 77~82%). 회차 간 차이가 큰데, 봇 패킷이 몰려 들어오는 정도에 따라 `WSASend` 횟수가 2,150 ↔ 3,270회/s로 달라지기 때문입니다.
- **틱 본문이 크게 줄었습니다**(분산·로그인 14~19 → 4.5~5.2ms, 200명 17~25 → 2.5~4.9ms). 틱 안에서 하던 `WSASend`가 틱 밖으로 나갔기 때문이며, P1a에서 남긴 "200명의 틱 본문 p99가 합격선에 가까움"도 이것으로 해소됐습니다(원인은 깨어난 몬스터의 AI가 아니라 틱 안에서 나가던 송신 비용이었던 것으로 보임 — 따로 분리 측정하지는 않음).
- **핫존 100 워커 1 대비**: 수정 후(워커 6)는 P1 전 워커 1(자연 묶임)과 핑이 같고(21~23 대 22~23) 틱 지연·묶임이 더 좋습니다(10~12 대 17ms, 14~23 대 6.6~7.5건), CPU는 비슷하거나 조금 높습니다(26~42 대 37~38).
- **워커 1 설정에서는 수정 후가 수정 전보다 나쁩니다**(핑 36~44ms, 틱 지연 22~32ms — 합격선 초과). 내보내기를 넘겨받을 다른 워커가 없어 같은 스레드가 다시 처리하기 때문입니다. 기본값(워커 6)이 아닌 설정이라 고치지 않았습니다 — `WorkerThreads=1`로 운영하지 않습니다.
- 한산한 곳(핫존 25)의 핑은 8~9 → 12ms로 늘었습니다(묶는 시간 T가 응답에 더해짐 — D-206의 "예외 없이 전부 묶음"에 따른 것, 대응은 CP1 클라이언트 선반영).
- 32회 모두 접속 실패·예상 밖 종료 0, `logDrop` 0, 서버 WARN·ERROR 0.

## chaos 램프 (`chaos.sh`, `runs/chaos/`)
Release 서버 하나에 `--bots 300 --ramp-rate 60 --profile hunt --chaos`를 ① 30초 끝까지 1회(접속·로그인 실패 0) ② 60초짜리를 9·12·15초에 강제 종료 3회. 마지막 종료 뒤 `[metrics]`가 `sessions=0 players=0`, `sendQ(total/sessionMax)=0/0`으로 돌아왔고 서버 생존, WARN·ERROR 0.
