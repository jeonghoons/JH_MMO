# DESIGN_WORLD — 필드 맵·인스턴스 던전·스폰 배치 (2026-11-17 사용자 승인, D-172)

마일스톤 1 월드 구간(ROADMAP L1~L4)과 인스턴스 던전(DG1~DG4)의 목표 설계입니다(D-167·D-170·D-171). 완료된 구현이 아니며, 수치는 L2a 파이프라인 시험과 블록아웃에서 확정합니다. 파티·인스턴스 던전의 패킷·상태 상세는 DG1에서 따로 설계합니다.

## 1. 목표와 범위
- 샘플 맵(`ParagonSample`)을 자체 맵으로 바꿉니다. 맵은 **두 개**입니다: 필드 맵 1개(마을 + 사냥터 2곳)와 인스턴스 던전 맵 1개.
- MS1 시연(마을 출발 → 사냥 → 드랍 → 줍기 → 장착 → 1:1 거래 → 상점)은 필드 맵에서 합니다. 파티·인스턴스 던전은 경매장과 함께 "Room 간 기능"으로 묶어 A5.2 전에 끝냅니다(위치는 사용자 확인 필요 — §8).
- 범위 제외였던 "다중 맵·포털"은 **인스턴스 던전 1개에 한해** 풉니다(D-171). 그 밖의 레벨 추가는 계속 제외입니다(같은 레벨 안의 포털은 L5에서 구현 — D-203, 마을/사냥터는 포털 기준으로 Room을 나눔 — D-215).
- 콘텐츠 동결(D-147)의 예외는 맵·환경 배치·NPC 배치까지입니다. 몬스터·NPC의 새 외형은 만들지 않습니다.

## 3. 맵 크기 점검
기준 수치: 플레이어 이동 5m/s(`PlayerStatTable.MoveSpeed` 500), 몬스터 4m/s, 시야 반경 50m(원 넓이 약 7,850㎡), 활 사거리 18m.

## 5. 제작 방식
- **필드 지면 = Landscape**. 높이맵을 스크립트로 만들어 넣고 `KiteDemo` 지면 타일을 레이어로 섞습니다.
- **던전 바닥·벽 = 스태틱 메시**(`Monolith/Ruins` 조립). Landscape를 쓰지 않으므로 지금 내보내기 도구로 바로 내비메시를 만들 수 있습니다.
- **마을 소품**: VARCO 3D로 6종 안팎(목책 조각, 입구 문틀, 가판대, 깃발, 모닥불, 상자·통) + 던전 횃불 1종. 건물은 만들지 않습니다.
- **Megascans는 쓰지 않습니다.** 지형에 깔았을 때 지면 재질이 부족하면 재질만 재검토합니다(Bridge·Fab 플러그인은 로드돼 있으나 Fab 창은 MCP로 조작할 수 없어 내려받기는 사용자가 해야 함).
- **몬스터**: 기존 Rampage 외형 그대로, `MonsterTable` 행을 늘려 스탯·크기로 단계를 나눕니다(약함·중간·던전·우두머리).
- **NPC**: 매니퀸 + 기존 천·판금 세트. 상점 NPC 1명(L4).
- **조명**: 필드는 야외 주간 고정, 던전은 어두운 고정 조명 + 횃불. 모두 동적 조명이며 라이트맵을 굽지 않습니다.
- **분담**: Claude가 높이맵·블록아웃·대량 배치·마커·서버 연결을 하고, 구역마다 위에서 본 캡처와 눈높이 캡처로 사용자 확인을 받습니다. 에디터 MCP에는 지형 조각·풀 칠하기 도구가 없으므로 필요한 것은 `jm_kit`/`JMEditorTools`에 함수를 만들어 씁니다.

## 7. 파티·인스턴스 던전 (개요 — 상세는 DG1)
**상세 설계는 [DESIGN_PARTY_DUNGEON.md](DESIGN_PARTY_DUNGEON.md)(2026-11-19 승인, D-215~D-219)입니다.** 아래는 2026-11-17의 개요이고, 다른 곳은 그 문서가 우선합니다 — 특히 정리 조건("전원 사망 시"가 아니라 "안에 아무도 없을 때"), 입장 방식(파티장이 같은 Room의 파티원과 함께), 정원(Room별 정원 없음·채널 500명).

파티별 인스턴스 던전은 서버 시연 가치가 큽니다: Room의 동적 생성·소멸, Room 간 플레이어 이동, Room을 넘는 전역 서비스(파티). 경매장(전역 `AuctionService`)과 같은 축입니다.

- **파티**: 최대 4명, 초대·수락·거절·탈퇴, 파티장. 파티원이 필드와 던전에 흩어질 수 있으므로 Room 밖의 전역 서비스(자체 JobQueue)로 둡니다. 저장하지 않습니다(접속을 끊으면 탈퇴).
- **입장**: 필드의 던전 입구(PortalTrigger 마커) 근처에서 요청 → 파티(없으면 혼자)의 인스턴스 Room이 없으면 생성 → 필드 Room에서 퇴장 처리(거래 취소, 진행 중인 아이템 작업 대기 — 저장은 하지 않고 도착 Room의 주기 저장이 이어받음, `DESIGN_PARTY_DUNGEON.md` §4-2) → 인스턴스 Room 입장 → 클라이언트에 맵 이동 통지 → 레벨 전환(대기 창) → 입장 완료.
- **인스턴스 수명**: 마지막 사람이 나가면 일정 시간 뒤 소멸. 지금 `RoomManager::Remove`가 비어 있어 방이 지워지지 않으므로 이때 구현합니다. 동시 인스턴스 수 상한을 둡니다. 내비메시는 맵별로 한 번만 읽어 공유합니다(A0.5의 맵 리소스 공유).
- **던전 규칙**: 몬스터 리스폰 없음, 우두머리 처치 = 클리어(드랍) → 출구 포털 또는 일정 시간 뒤 필드 마을로. 안에 아무도 없으면(들어오는 중인 사람 포함) 바로 정리(D-218·D-225 — 전원이 죽어도 유지). 던전 안에서 끊고 재접속하면 필드 마을에서 시작합니다(단순하게).
- **클라이언트**: 맵 이동 통지를 받으면 레벨 전환 + 오브젝트 정리, 파티 창(초대·목록), 입장 확인.
- **부하 시험**: 봇 프로파일에 "파티 맺기 → 입장 → 사냥 → 퇴장" 반복을 넣어 Room 생성·소멸이 계속 일어나는 상황을 잽니다(A5.2).
- **정해야 할 것(DG1)**: 패킷 번호·상태 전이, 입장 중 접속 해제·중복 요청·파티 변경 처리, 인스턴스 상한을 넘었을 때의 응답, 드랍 소유권(파티 공유 여부), 필드 채널 선택 방식.

### 11-1. 코드 조사로 확인한 것

### 11-2. 만들 것
1. **C++ `ULandscapeBuildLibrary`**(`JMEditorTools`, 에디터 전용): `CreateLandscape(높이 파일(.r16), 한 변 정점 수, 정점 간격 cm, 높이 배율, 재질)` — 열린 레벨에 Landscape 하나를 만들고 결과를 문자열로 돌려줌(실패는 `ERROR:`). `ReplaceHeights(...)` — 같은 Landscape의 높이만 다시 넣음(L2b에서 기복을 여러 번 고칠 때 씀).
2. **`MapExportCommandlet` 지형 내보내기**: 위 표대로. 로그에 지형 컴포넌트 수·삼각형 수를 따로 찍음. 스태틱 메시 규칙(충돌 켜짐 + Pawn Block)은 그대로.
3. **Python `jm_kit.world`**: 높이맵 생성기(표준 라이브러리만 — 평지·경사로·언덕·가장자리 능선을 식으로 합성해 `.r16` 저장), 구역 정의(JSON)에서 마커 좌표 계산.
4. **`jm_mcp` `WorldTools`**: `world_new_level`, `world_build_landscape`, `world_replace_heights`. 마커·바위 배치는 공식 `SceneTools`·`ObjectTools`를 그대로 씀.
5. **서버**: 코드 변경 없음(맵 이름 전환 방법은 11-5의 확인 사항).

## 13. 레벨·Room 분할 방식 비교 (2026-11-17, §0 용어로 다시 씀)
"대륙의 야외 맵들을 레벨 하나에 두는 것이 맞는가, Room은 어떻게 나누는가"에 대한 비교입니다. 클라이언트의 **레벨**과 서버의 **Room**은 서로 다른 축이라 따로 정할 수 있습니다.

### 13-1. 코드·측정으로 확인한 사실
| 사실 | 근거 |
|---|---|
| Room 하나는 JobQueue 하나라 그 안의 일은 직렬로 처리된다. 병렬은 Room과 Room 사이에서만 일어난다 | `Room::PushJob`·`ReserveJob`, 틱은 `Room::Update`가 100ms마다 `_objects` 전체를 순회 |
| 같은 레벨을 쓰는 Room이 이미 여러 개 생긴다. 정원 100명이 차면 새 Room을 만든다(월드 전체 복제인 "채널"과는 다름) | 조사 당시 `Room.h` `MAX_ROOM_CAPACITY = 100`(2026-11-17 `WorldTable.RoomCapacity`로 옮김, D-176), `RoomManager::EnterPlayer`·`TryEnterExisting` |
| 내비메시는 레벨별로 한 번만 읽고 Room들이 공유한다 | `NavmeshManager`의 `GNavCache` |
| Room 10개 × 100명(120m 레벨)에서 틱 본문 p99 5~13ms(합격선 20ms), 워커 6이 최선, 워커 1이면 Room 10개가 직렬화돼 악화 | `PERF_BASELINE_2026-11-06.md` §3·§4 H3 |
| 한 Room 안에 100명이 반경 10m에 몰리면 핑 p99 146~173ms로 초과. 원인은 틱 계산이 아니라 수신자별 송신 호출 | 같은 문서 H2·H3 (P1 송신 묶기의 대상) |
| 빈 Room 삭제는 구현이 비어 있다 | `RoomManager::Remove(shared_ptr<Room>)` |

- "Room이 커질수록 병렬성이 떨어진다"는 맞습니다. Room 하나는 한 번에 코어 하나만 씁니다. 병렬성을 정하는 것은 레벨을 몇 개로 나누느냐가 아니라 **Room 하나에 얼마나 많은 일을 넣느냐**입니다.
- **Room을 복제해 인원만 늘리는 것은 지양합니다(D-173).** 100명짜리 Room 50개는 서로 만나지 않는 100명 서버 50개와 같습니다. 목표는 Room당 수용 인원을 측정으로 올리고, 채널 하나가 담는 인원(= 맵별 Room 정원의 합)을 키우는 것입니다.
- §3의 "채널당 약 500명"은 근거 없는 가정이었습니다. 한 Room에 100명을 넘겨 잰 적이 없습니다.

### 13-2. 가능한 조합
| 안 | 클라이언트 레벨 | 서버 Room | 맵을 넘을 때 |
|---|---|---|---|
| A. 레벨 하나 = Room 하나 | 대륙의 야외 맵 전부를 한 레벨에 | 레벨 전체가 Room 하나 | 넘는 것이 없음(이어져 있음) |
| B. 맵마다 레벨 | 마을 / 초원 / 숲을 따로(또는 마을+초원 / 숲) | 레벨마다 Room | 포털 → 로딩 화면 → 다른 Room |
| C. 레벨 하나 + 맵별 Room | 대륙의 야외 맵 전부를 한 레벨에 | 같은 레벨을 맵 경계선으로 나눠 맵마다 Room | 경계 통로를 지나면 로딩 없이 Room만 바뀜. 경계 건너편은 보이지 않음 |
| D. 이어진 공간 분할 | 한 레벨 | 격자로 나눈 Room들이 경계 너머를 서로 보여 줌 | 완전히 이어짐(경계 양쪽이 서로 보이고 싸움) |
| E. Room 내부 병렬화 | 한 레벨 | Room 하나, 틱을 여러 스레드로 | 넘는 것이 없음 |

어느 안이든 던전은 별도 레벨이고 파티마다 인스턴스(Room)를 만듭니다. 대륙 사이의 이동(배)은 레벨 전환입니다.

| 300m | 약 63,500㎡ | 500 | 약 62 |
| 200m | 약 28,900㎡ | 100 | 약 27 |

- 측정으로 확인된 범위는 "Room당 100명"뿐입니다. 그 이상은 틱 본문 시간을 새로 재야 합니다(몬스터 80마리 포함).
- 한 사람이 받는 송신량은 Room 인원이 아니라 시야 안 인원에 비례하므로, 넓은 레벨은 Room 인원을 늘리기에 유리합니다. 틱 계산은 Room 인원과 깨어 있는 몬스터 수에 비례합니다.

### 13-4. 안별 장단점과 필요한 것
**A. 레벨 하나 = Room 하나**
- 기술: 추가 서버 작업 없음. 마을 인파와 사냥이 한 시야에 이어짐. 대륙의 야외 인원 전부가 한 Room이라 Room이 가장 큼 — 수용 인원이 Room 하나의 한계에 묶임.
- 관리: 레벨·정의 파일·내보내기·내비메시가 1벌. 봇 배치와 기준선이 단순.
- 필요: Room 정원을 상수에서 테이블 값으로, 정원별 틱 측정.

**B. 맵마다 레벨**
- 기술: 맵마다 Room이라 일이 나뉨. 레벨이 작아 내비메시 한 타일 상한 위험이 줄어듦. 맵을 넘을 때마다 로딩. 레벨 전환 기능은 던전·대륙 이동용으로 어차피 만듦.
- 관리: 레벨마다 정의 파일·경계 능선·조명·내보내기·테이블 행. 분위기가 같은 레벨을 따로 관리하는 중복. 봇이 레벨을 골라 들어가야 함.
- 필요: 맵 사이 포털과 이동 처리, Room마다 레벨 선택, 클라이언트 레벨 전환·로딩 화면.

**C. 레벨 하나 + 맵별 Room**
- 기술: 같은 분위기는 한 레벨에 두고 서버만 맵으로 나눔. 로딩 없이 넘어감. Room 간 이동은 던전용 것을 쓰고 레벨 전환만 뺌. 내비메시는 한 장을 공유. 단점은 경계 건너편 사람·몬스터가 보이지 않는 것 — 경계를 바위로 꺾인 좁은 통로에 두어 가려야 함. 경계 근처의 추격·투사체·드랍·거래는 끊기는 규칙이 필요.
- 관리: 레벨·내보내기는 1벌이고 마커에 맵 번호만 추가. 통로 지형을 구도에 넣어야 함.
- 필요: 맵 경계 정의(마커), 스폰의 맵 필터, 경계 통과 시 Room 이동, 경계 규칙, 클라이언트의 Room 전환 처리(오브젝트 정리).

**D. 이어진 공간 분할**
- 기술: 가장 강한 서버 시연이지만 "Room의 데이터는 그 Room의 작업에서만" 규칙을 깸. 경계 너머 복제(유령 오브젝트), 경계를 걸친 전투·시야·드랍·거래, 이동 중 아이템 작업 인계가 모두 필요. 복제·손실 버그 위험이 가장 큼.
- 관리: 검증 범위가 서버 전체에 걸침. 일정 예측이 어려움.
- 필요: Room 간 메시지 규약, 유령 오브젝트, 인계 프로토콜, 전 기능 재검증. **범위 밖으로 권함.**

**E. Room 내부 병렬화**
- 기술: 레벨 분할과 무관한 선택. 틱을 나누려면 Room 데이터에 락이나 단계 분리가 필요. 지금 병목은 계산이 아니라 송신 호출이라(H2·H3) 효과가 불확실.
- 관리: 동시성 버그 위험. 이미 계획된 P1(송신 묶기)·P4(몬스터 AI)와 겹침.
- 필요: 측정으로 틱 계산이 병목임이 확인된 뒤에만 검토. **지금은 하지 않음.**

### 13-5. 정리
- 실제로 고를 수 있는 것은 **A·B·C**입니다. D·E는 비용과 위험이 범위를 넘습니다.
- "같은 분위기는 같은 레벨"과 "Room이 커지면 병렬성이 떨어진다"는 **C**로 함께 만족됩니다. A는 측정에서 Room 하나가 대륙의 야외 인원을 감당할 때만 맞습니다.
- 어느 안으로 갈지와 레벨 크기는 §14의 측정 뒤에 정합니다. C는 A의 레벨 위에 경계만 추가하므로 A로 시작해도 만든 레벨을 버리지 않습니다.

## 14. Room 분할 구조와 측정 계획 (D-173, §0 용어로 다시 씀)
Room은 작업 큐입니다. 무엇을 한 큐에 묶을지는 어느 단위로도 정할 수 있어야 하고, 어느 단위가 맞는지는 측정으로 정합니다.

### 14-1. Room을 나누는 단위
| 나누는 기준 | Room 하나가 맡는 것 | 경계를 넘을 때 | 지금 코드 |
|---|---|---|---|
| 채널 | 한 채널의 것만(채널은 월드 전체의 복제) | 채널 변경 — 서로 만나지 않음 | 없음(100명마다 Room을 하나 더 만드는 것뿐) |
| 레벨 | 레벨 하나 전체 | 레벨 전환(로딩) | 모든 Room이 한 레벨(`ServerConfig` `[World] MapName`) |
| 맵 | 레벨 안의 맵 하나(마을·초원·숲). 경계는 마커로 정의 | 로딩 없이 Room만 바뀜 | 없음 |
| 인스턴스 | 파티 하나의 던전 | 입장·퇴장(레벨 전환) | 없음(DG3) |

- 기본 후보는 **Room = (채널, 맵)**, 던전은 **Room = (파티, 던전 맵)**입니다. 맵을 "레벨 전체 하나"로 두면 A안, 맵 행을 늘리면 C안, 레벨을 늘리면 B안입니다. **구조는 하나이고 데이터로 고릅니다.**
- 채널 하나가 담는 인원 = 그 채널의 맵별 Room 정원의 합입니다. 맵과 대륙이 늘수록 Room을 복제하지 않고도 한 월드의 인원이 늘어납니다.
- 큐를 나누는 것은 자유지만 **경계에서 무엇이 보이느냐가 비용**입니다. 레벨 경계는 로딩이 가려 주고 채널은 원래 만나지 않습니다. 같은 레벨 안의 맵 경계만 "건너편이 안 보임"을 지형(꺾인 통로)으로 가리거나 복제(D안, 범위 밖)해야 합니다.
- 필요한 변경(초안): 테이블을 (레벨, 맵) 행으로 — 정원·시야 수치·맵 범위, Room이 자기 맵을 알고 그 맵의 스폰만 생성, `RoomManager`가 (채널, 맵)으로 Room을 찾음, 플레이어가 채널 번호를 갖고 이동해도 같은 채널에 머묾, Room 간 이동(DG3과 공유), 빈 Room 삭제.
