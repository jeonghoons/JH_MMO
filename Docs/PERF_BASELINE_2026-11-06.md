## 4. 병목 가설별 판정
- **H1 커널 네트워크 비중 — 확인.** 커널/사용자 시간(코어 1개=100%): 분산 1,000 사용자 27 / 커널 108(80%), 핫존 100 6 / 64(91%), 핫존 100 워커 1은 5 / 13. 커널 시간이 WSASend/TCP 자체인지 IOCP 완료 통지로 다른 워커를 깨우는 비용인지는 샘플링을 못 해 구분 불가(H3는 후자 몫이 큼을 시사).
- **H2 수신자별 WSASend 1:1 — 확인.** `Session::Send`는 `_sendRegistered`가 아니면 즉시 `RegisterSend()`→`WSASend`. 핫존 100(워커 2 이상)에서 `sessionMax`가 항상 1. 메시지 1건당 서버 비용 ≈ 0.70코어 ÷ 36.5k ≈ 19µs(커널 17.5 + 사용자 1.7). `Send(…, pushOnly=true)` 인자는 있으나 미사용.
- **H3 IOCP 워커 수/방 수 경쟁 — 확인(가장 큰 발견).**

  | 실행 | 워커 | 핑 p99 | 틱 지연 p99 | 서버 CPU(코어1 환산) | sessionMax | 비고 |
  |---|---|---|---|---|---|---|
  | 핫존 100 | 1 | 36.7 | 16~18 | 16% | 76~82 | 합격선 통과(틱 본문 p99 8~12) |
  | 핫존 100 | 2 | 147 | 146~149 | 70% | 1 | 워커 6과 같음 |
  | 핫존 100 | 6 | 146~173 | 147~250 | 65~75% | 1 | 기본 |
  | 분산 1,000 | 1 | 81 | 34~40 | 41% | 45~50 | 방 10개 직렬화 |
  | 분산 1,000 | 2 | 58 | 17~29 | 67% | 34~47 | 순간 적체(total 1.5k~12.6k) |
  | 분산 1,000 | 6 | 47 | 18~30 | 121% | 44~50 | 기본 |
  | 분산 1,000 | 12 | 81 | 74~91 | 235% | 30~44 | 봇 비정상 종료 3, 악화 |

  해석: 핫존(방 1개)은 어차피 한 워커만 방 잡을 처리한다. 워커 1개면 드레인 중 완료 처리가 미뤄져 세션 큐에 ~80건이 쌓였다가 WSABUF 80개로 WSASend 1회 → 같은 송신량에서 CPU −77%. 워커 2개부터 묶임이 사라져 비용 4배. 분산에서는 기본 6(물리 코어 수, `ResolvedWorkerThreads` = 논리코어/2)이 최선. **워커 수를 늘리는 건 해법이 아니고, 호출 수를 줄이는 P1이 맞다.**
- **H4 송신 큐 적체 — 기각.** 지금은 적체가 아니라 호출 비용 문제(핫존 100 total 0 / sessionMax 1, 분산 1,000 sessionMax 44~50은 입장 직후 `SC_ADD_OBJECT` 묶음).
- **H5 락 경합 — 미확인**(샘플링 권한 없음). 핫존은 방 1개라 게임 로직 락 경합은 구조상 없다. 워커 2개 이상에서 비용 4배는 IOCP 완료 통지·스레드 깨우기, 같은 `SendBuffer` `shared_ptr` 참조 카운트의 캐시라인 경합, 소켓 내부 락 쪽을 가리킨다(추정).
- **H6 같은 PC 봇 왜곡 — 핫존 100은 영향 없음(확인), 분산 1,000은 작음(추정).** 서버 CPU 0~5 / 봇 6~11 어피니티 분리해도 핑 p99 146ms, 서버 68%로 같았다.
- **H7 부 병목 = 깨어난 몬스터 AI — 유지.** 틱 본문 p99 분산 1,000 5~13ms(max 24). P1 뒤에도 P4가 필요할 수 있다.

## 5. P1 기대 효과(추정)와 설계 주의점
| 시나리오 | 현재 | P1 후 기대 | 근거 |
|---|---|---|---|
| 핫존 100 | 핑 p99 150~173, 틱 지연 p99 150~250, CPU 70%(코어1) | 핑 p99 ≤ 50, 틱 지연 p99 ≤ 20, CPU 15~25% | 워커 1 자연 실험 37 / 17 / 16% |
| 핫존 50 | 52(요동) | ≤ 30 | 같은 원리, 묶음 작음 |
| 분산 1,000 | 47 / 18~30 / 1.2코어 | 핑 p99 30~40, CPU 0.5~0.8코어(폭 큼) | 방당 잡 600/s·수신자 30명, 드레인당 잡 3~10개일 때만 세션당 2~5건 묶임. 몬스터 AI 몫은 P4 |
| 로그인 폭주 | 통과 | 통과 유지 | |

설계 주의점(감사 결과와 일치):
1. `JobQueue::ExecuteJobs`는 큐가 빌 때까지 돈다 → 포화 상태에서는 "작업 묶음 끝"이 거의 오지 않아 끝에서만 보내면 송신이 굶는다. **잡 N개(16~64) 또는 시간 상한(1~2ms)마다 보내기**가 필요하다(감사 F5와 같은 수정).
2. 묶기 단위 = 드레인 중 Send된 세션 집합, 보낼 때 세션당 `RegisterSend` 1회. 기존 `Send(pushOnly)`와 `ProcessSend`의 재확인 경로를 재사용.
3. 효과 지표를 먼저 추가: `NetStats::SendCalls`(WSASend/s)와 WSABUF 평균 개수(= out/s ÷ SendCalls).
4. `WorkerThreads`는 기본 유지.

재측정 계획: 같은 매트릭스(분산 1,000 / 핫존 25·50·100 / 로그인 1,000)를 같은 인자로 각 2회 이상. 추가 비교 = 핫존 100 워커 1(P1 전) vs 워커 6(P1 후) — P1이 자연 묶음 수준에 도달했는지가 완성 기준. 합격선 = 기존 유지 + 핫존 100 핑 p99 ≤ 50 / 틱 지연 p99 ≤ 20 / 서버 CPU 코어1 환산 ≤ 25%, 분산 1,000 핑 p99 ≤ 40, WSABUF 평균 ≥ 10(핫존 100). 분산 2,500은 봇 CPU를 함께 기록하고 해석 보류. CPU 샘플링은 관리자 셸에서.

## 6. 이상 현상·도구 문제
1. A1.3 매트릭스의 LoadTest CSV·서버 로그가 보존되지 않았고 `metrics.csv`는 avg/max만 있어 p99 재검토 불가 → 매트릭스 실행 시 `--out`에 날짜·시나리오 이름, 서버 로그 보관.
2. `metrics.csv`는 append라 서버 재시작마다 헤더가 반복 삽입(`tellp()==0` 검사가 재시작에서는 거짓)되고 PIE 실행 등이 섞인다 → 실행 ID 열 제안.
3. `GetProcessIoCounters`로는 WSASend를 셀 수 없다(other ops ≈ WSARecv 수만 집계).
4. xperf/WPR/VSDiagnostics는 관리자 권한 필요.
5. 유휴 tickLate avg 6.6~7ms = 타이머 해상도 기저값(`timeBeginPeriod(1)`로 낮출 수 있으나 P1 범위 밖).
6. 분산 1,000 워커 12에서 봇 비정상 종료 3건(서버 로그 오류 없음, 원인 미확인). 기본 설정에서는 전 시나리오 실패 0.
7. 핫존 25·50 핑 p99가 5초 구간마다 15~29 / 20~65ms로 요동(봇 200ms 주기와 ramp 위상 뭉침 추정) → 2회 이상 반복.
