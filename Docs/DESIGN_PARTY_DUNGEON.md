# 파티·인스턴스 던전·Room 간 이동 상세 설계 (DG1)

상태: **승인** (2026-11-19, D-215~D-219 — `[제안]` 표시 항목도 이 승인으로 확정. 수치 가운데 마을 시작 지점 위치와 인스턴스 상한은 해당 단계에서 다시 확인). 구현은 DG2·DG3·DG4. 개요는 [DESIGN_WORLD.md](DESIGN_WORLD.md) §7·§14-1, 용어는 §0(대륙·맵·레벨·채널·인스턴스·Room).

표시: **[결정]** = 사용자가 정한 것(2026-11-19 또는 그 전 결정 번호), **[제안]** = 이 문서가 제안하는 것(승인하면 확정), **[그대로]** = 지금 동작을 유지.

---

## 1. 범위

만드는 것:
1. **Room 모델**: Room이 자기 종류·채널·맵을 알고, 방마다 다른 레벨을 쓸 수 있게 함.
2. **포털 기준 Room 분할**: 마을 / 사냥터 / 던전 인스턴스. [결정]
3. **Room 간 이동**: 접속을 유지한 채 한 Room에서 다른 Room으로 옮기는 절차(같은 레벨 안, 다른 레벨로).
4. **채널 자동 배정**. [결정]
5. **파티**(전역 서비스, 최대 4명 — D-171).
6. **인스턴스 던전**: 파티별 생성·입장·퇴장·소멸.

하지 않는 것:
- 이어진 지형을 걸어서 넘는 Room 경계(사냥터 안의 초원 3곳·숲은 한 Room). 경계 규칙(추격·투사체·드랍)이 필요 없습니다.
- 채널 선택·변경 UI, 다른 채널 사람과의 파티.
- 정거장 포털 110(→ `Continent02`): 계속 거부. [제안]
- 파티 추방, 파티원 HP 표시, 분배 규칙(주사위·순번), 파티 채팅. [결정: 추방 없음 / 그 밖 제안]
- 던전 난이도·재입장 제한·기록 저장.

## 2. Room 모델

### 2-1. Room 종류와 키

| 종류 | 키 | 레벨 | 만들어지는 때 | 없어지는 때 |
|---|---|---|---|---|
| 마을 | (채널, `Town`) | `Continent01` | 그 채널이 처음 필요할 때 | 없어지지 않음 |
| 사냥터 | (채널, `Field`) | `Continent01` | 마을 Room과 함께 | 없어지지 않음 |
| 던전 인스턴스 | 인스턴스 번호(파티 또는 혼자인 플레이어 소유) | `Continent01_Dungeon` | 입장 요청 때 | 빈 채로 일정 시간 뒤(§6-5) |

- Room은 `roomId`·`kind`·`channel`·구역 이름(`town`/`field`/`dungeon`)·레벨 이름을 필드로 갖습니다. 지금은 Room이 자기 id도 맵 이름도 모르고 모든 판단이 `GServerConfig.mapName` 하나에 묶여 있습니다(`Room.cpp:21, 568, 613` 등 10곳) — 전부 "이 Room의 값"으로 바꿉니다.
- `ServerConfig` `[World] MapName`은 **로그인한 플레이어가 처음 들어가는 레벨**(= 마을이 있는 레벨)이라는 뜻으로 남깁니다.
- 채널 1의 마을·사냥터 Room은 서버 시작 때 만듭니다(지금과 같이 시작 로그에서 맵 로드 오류를 바로 봄). 채널 2 이상은 필요할 때 만들고, 한번 만든 채널은 서버가 꺼질 때까지 둡니다. 빈 채널 정리는 본 부하 테스트(A5.4)에서 필요하면 넣습니다.

### 2-2. 정원 [결정: Room별 제한 없음, 채널 500명]

- **Room마다의 정원은 두지 않습니다.** 제한은 **채널 하나에 500명**뿐입니다(그 채널의 마을·사냥터·던전에 있는 사람을 모두 합한 수). 포털 이동과 부활은 정원 때문에 거부되는 일이 없습니다.
- 데이터: `WorldTable.RoomCapacity` 열을 `ChannelCapacity`로 바꾸고 `Continent01` 행에 500을 넣습니다(서버 전용 열). 구역별 테이블은 만들지 않습니다 — 마을·사냥터 구분은 마커의 구역 이름(§2-3)으로, 던전은 `WorldTable`의 던전 레벨 행으로 충분합니다.
- 채널 인원은 `WorldService`가 셉니다(로그인 때 +1, 접속이 끝나 정리될 때 -1). Room의 `TryReserveSlot`·`_capacity`는 없앱니다.
- **알아 둘 한계**: 제한이 없으므로 500명이 한 Room에 몰릴 수 있습니다. RC2 측정(Room 하나)에서 분산 500명은 틱 지연 p99 34~35ms로 합격선(20ms)을 넘었고 마을에 500명이 모이면 핑 p99 125~132ms였습니다(둘 다 무너지지는 않음). 마을과 사냥터가 서로 다른 Room(= 다른 스레드)이 되고 마을 시작 지점을 나누므로(§2-3) 평소에는 이보다 낫겠지만, 채널 500명이 합격선 안인지는 DG3b 완료 기준에서 직접 잽니다(마을·사냥터에 나눠 500명 / 한쪽에 몰아 500명). 결과가 나쁘면 그때 채널 정원을 낮추는 것이 조정 수단입니다. D-209(`RoomCapacity` 250)·D-178의 "마을 150·사냥터 150"은 이 결정으로 대체됩니다.

### 2-3. 마커의 구역

같은 레벨을 마을 Room과 사냥터 Room이 함께 쓰므로, 맵 마커(로직 JSON)에 **구역 이름 `area`** 를 넣습니다. [제안]

- `town`: 시작 지점(PlayerStart — 여러 곳, 아래), 상점 NPC, 안전 구역, 마을 쪽 포털 101·102·103.
- `field`: 몬스터 스폰 49곳, 사냥터 쪽 포털 201·202·203, 던전 입구 100, 정거장 110.
- Room은 자기 구역의 마커만 씁니다(스폰·NPC·포털 목록). 내비메시는 레벨 전체를 그대로 공유합니다(마을 문은 닫힌 충돌이라 걸어서 나갈 수 없음 — L5).
- **마을 시작 지점을 여러 곳에 둡니다** [결정]: 로그인·부활·던전에서 내보내질 때 한 자리(광장 모닥불)에 겹쳐 서지 않게 마을 안에 PlayerStart 마커를 여러 개 놓고, 서버가 그중 하나를 고릅니다. [제안] 4곳 — 광장(지금 자리)과 서·동·북 문 안쪽 광장 쪽 빈터. 고르는 방법은 차례대로 돌아가며(사람이 고르게 나뉨), 고른 마커 중심에서 반경 3m 안의 무작위 자리(내비메시 위로 보정)에 세웁니다. 위치는 DG3b에서 맵을 보고 정하고 승인받습니다. 지금 서버는 PlayerStart 첫 번째만 쓰고(`Room.cpp:222-228`) 부활 자리를 "입장 때 배치된 자리"로 기억하는데, 마을은 "매번 새로 고른 시작 지점", 던전은 "던전 시작 마커"로 바꿉니다.
- 포털의 도착 Room = 도착 마커(`targetMap` + `targetPointId`)의 구역. 그래서 101 → 201은 "마을 Room → 같은 채널의 사냥터 Room"이 됩니다.
- 제작: `jm_kit.world`의 `world_place_markers`가 정의 파일의 구역 값을 마커에 쓰고, `MapExportCommandlet`이 JSON에 내보냅니다(L3에서 `zone`을 넣은 것과 같은 경로). 안전 구역은 마을 Room에만 있으므로 사냥터 Room의 "안전 구역" 검사는 자연히 빠집니다 — 사냥터 몬스터가 마을 벽 근처까지 추격하는 것은 추격 제한(`LeashRangeCm`)이 그대로 막습니다.

### 2-4. 채널 [결정: 자동 배정]

- 플레이어는 로그인할 때 채널 번호를 받고 **접속이 끝날 때까지 그 채널**에 있습니다(`Player::channel`).
- 배정: 인원이 `ChannelCapacity`(500) 미만인 가장 낮은 채널. 모든 채널이 찼으면 새 채널(마을 + 사냥터 Room)을 만듭니다.
- 채널 안에서는 정원 때문에 이동이 막히지 않습니다(§2-2).
- 던전 인스턴스는 채널에 속하지 않지만, 파티가 같은 채널 사람으로만 만들어지므로(§5) 인스턴스 안의 사람도 같은 채널입니다. 나올 때 자기 채널의 마을로 갑니다.
- 더미 봇(`is_dummy`)도 같은 규칙으로 채널을 받습니다. 지금의 "정원이 차면 같은 Room을 하나 더" 동작(`RoomManager::EnterPlayer`)은 이 규칙으로 대체됩니다. 부하 측정에서 한 채널에 몰아넣는 시험은 지금처럼 임시 테이블(`JH_DATA_DIR`)로 채널 정원을 올려서 합니다.

## 3. 전역 서비스 `WorldService` [제안]

파티·인스턴스·채널 배정·"누가 어디 있는지"를 한 서비스가 맡습니다. `AuthLobby`와 같은 꼴(자체 `JobQueue`, 전역 `GWorld`, 서비스 상태는 그 잡 안에서만 읽고 씀)입니다.

- **접속자 명부**: `PlayerUID → { 이름, 세션(weak), 채널, 지금 있는 Room(weak)·종류, 파티 번호 }`와 `이름 → PlayerUID`. 캐릭터 이름은 DB에서 유일합니다(`IX_Player_Info_Name`). Room이 입장·퇴장·이동 때 서비스에 알려 갱신합니다. 더미 봇은 이름이 모두 같아 이름 색인에는 넣지 않습니다(파티 초대는 오브젝트 id로만).
- **Room 목록·생성**: 채널별 마을·사냥터 Room, 던전 인스턴스 목록과 상한. Room 생성(`InitRoom`, 첫 로드 약 0.1초)은 이 서비스의 잡에서 합니다 — 지금은 IOCP 수신 스레드가 `_createMutex`를 잡고 맵을 읽어 다른 입장을 막습니다(2026-11-06 감사).
- **파티 상태**(§5), **인스턴스 소유 관계**(§6).
- 서비스가 플레이어에게 보내는 패킷은 세션에 직접 보냅니다(잡 큐 밖 송신이라 묶이지 않고 바로 나감 — 양이 적음).
- Room이 알아야 하는 것은 서비스가 그 Room 잡으로 알려 줍니다: 플레이어의 파티 번호(`Player::partyId` — 드랍 소유권 판정용).

`RoomManager`는 "roomId → Room" 보관소로만 남고(지표 리포터가 순회), 배정·생성·제거 판단은 `WorldService`가 합니다.

## 4. Room 간 이동 절차

지금은 "세션은 붙어 있는데 방만 나가는" 경로가 없습니다(퇴장 = 접속 해제 하나뿐, `GameSession.cpp:22`). 새로 만드는 핵심 절차입니다.

### 4-1. 이동이 일어나는 경우

| 경우 | 요청 | 도착 |
|---|---|---|
| 마을 ↔ 사냥터 | `CS_PORTAL`(문 포털, 지금 패킷 그대로) | 같은 채널의 상대 Room, 도착 마커 자리 |
| 던전 입장 | `CS_PORTAL`(입구 100) | 인스턴스 시작 마커 |
| 던전 퇴장 | `CS_PORTAL`(던전 안 출구 포털) | 자기 채널 사냥터 Room의 입구 100 앞 [결정] |
| 던전에서 내보냄 | 서버(파티 탈퇴, 클리어 뒤 시간 종료) | 자기 채널 마을 Room의 시작 지점 중 하나 |
| 사냥터에서 부활 | `CS_REVIVE` | 자기 채널 마을 Room의 시작 지점 중 하나 [결정] |
| 던전에서 부활 | `CS_REVIVE` | 같은 인스턴스의 시작 마커(Room 이동 아님) [결정] |

- 사냥터에서 죽으면 마을에서 부활: 지금도 부활 자리는 PlayerStart(마을)이고(D-149), 마을이 다른 Room이 되므로 Room 이동이 됩니다. 이 이동은 "죽은 채로 요청 → 도착해서 살아남"이라 ①의 생존 검사 대신 부활 검증(대기 시간)을 쓰고, HP 회복·`SC_REVIVE` 방송은 도착 Room의 입장 마무리에서 합니다(떠난 Room의 사람들에게는 `SC_REMOVE_OBJECT`만 감).
- 접속을 끊었다 다시 들어오면 어디에 있었든 마을에서 시작합니다(D-151 — 위치는 저장하지 않음, [그대로]).

### 4-2. 순서

```
출발 Room 잡                WorldService 잡              도착 Room 잡
① 요청 검증
② 끝나지 않은 일 대기
③ 이동 표시(transfer) ──→ ④ 도착 Room 찾기·만들기
                            인스턴스는 닫힘 방지
⑤ 떠나기 처리 ←──────────── (실패면 결과만 알림)
   _ownerRoom = 도착 Room ────────────────────────→ ⑥ 들어오기 처리
                                                     SC_ROOM_CHANGE
                            ⑧ 명부 갱신 ←──────────── ⑦ (레벨이 다르면 로딩 완료 대기)
```

① **요청 검증**(출발 Room): 생존, 시전·이동 잠금 아님, 포털 재사용 대기, 포털 존재·거리(지금 `PlayerUsePortal`의 검증 그대로) + 이미 이동 중이 아님. 던전 입장은 §6-2의 조건 추가.

② **끝나지 않은 일 대기** [결정: 끝날 때까지 기다렸다 이동]:
- 기다리는 것: DB에 가 있는 아이템 작업(`itemOp.inFlight`), 확정 처리 중인 1:1 거래(`CONFIRMING`), 진행 상황·액티브 칸 저장(`progressSave`·`quickSlotSave`).
- 플레이어에 "이동 대기"를 걸고, 위 작업의 결과 처리 끝에서 다시 확인해 모두 끝났으면 ③으로 갑니다.
- 대기 중: 새 아이템·거래·상점·장착 요청은 `BUSY`로 거부, 이동·전투는 그대로 받습니다. 대기 중에 죽거나 접속이 끊기면 이동을 취소합니다. `MoveWaitTimeoutMs`(5초, [제안]) 안에 끝나지 않으면 취소하고 `MOVE_RESULT_TIMEOUT`.
- 이렇게 하면 **DB 결과가 옛 방으로 돌아오는 일이 없습니다** — 지금 구조(결과를 요청한 Room 잡으로 돌려줌, 그 방에 없으면 메모리 반영을 건너뜀)를 바꾸지 않고 "DB와 메모리가 어긋나는" 문제를 막습니다.

③ **이동 표시**: `Player::transfer`를 켭니다. 켜져 있는 동안 그 플레이어의 모든 요청(이동·공격·아이템·포털)을 버립니다. 같은 요청이 또 와도 무시됩니다(중복 요청 방지).

④ **도착 Room 찾기**(WorldService): 종류에 따라 채널의 상대 Room 또는 인스턴스를 찾고(없으면 만들고), 인스턴스면 "들어올 사람" 수를 올려 둡니다(그동안 닫히지 않게 — §6-5). 실패(인스턴스 상한·클리어한 인스턴스 등)면 출발 Room에 알려 `transfer`를 끄고 `SC_MOVE_RESULT`를 보냅니다.

⑤ **떠나기 처리**(출발 Room, 지금 `PlayerLeaveRoom`에서 "접속 해제 전용"을 뺀 것):
- 그 사이 죽었거나(부활 이동은 제외) 끊겼으면 이동을 취소하고 서비스에 알림(인스턴스의 "들어올 사람" 수를 되돌림).
- 확정 전의 1:1 거래 취소(`TRADE_RESULT_MOVED` 신설 [제안]), 조준 해제, 시야에서 빼기(남은 사람들에게 `SC_REMOVE_OBJECT`), `_players`·`_objects`에서 뺌.
- 하지 않는 것: 진행 상황 저장 요청(②에서 끝난 상태이고 데이터는 `Player` 객체가 들고 감 — 주기 저장은 도착 Room이 이어받음), `NotifyClosedIfDone`.
- 피격 경직·행동 잠금·몬스터의 추격 대상에서는 자연히 빠집니다(몬스터는 대상이 방을 나가면 포기 — D-193).
- `_ownerRoom`을 도착 Room으로 바꾸고 도착 Room에 ⑥을 넣습니다. 이 뒤에 온 패킷은 도착 Room 큐로 가고(⑥ 뒤에 실행됨), 출발 Room 큐에 남아 있던 그 플레이어의 작업은 "방에 없음"으로 버려집니다.
- `_ownerRoom`은 Room 잡이 쓰고 IOCP 수신 스레드가 읽으므로 원자적으로 읽고 쓰게 바꿉니다(지금은 입장 때 한 번만 써서 문제가 없었음).

⑥ **들어오기 처리**(도착 Room):
- 세션이 끊겼으면 `NotifyClosedIfDone`(지금 `PlayerEnterRoom` 첫머리와 같음).
- 위치 = 도착 지점(지금은 항상 PlayerStart로 덮어씀 — 도착 지점을 받게 바꿈), 속도 0, 이동 보정 순번 +1·이동 예산 0(**순번을 0으로 되돌리지 않음** — 클라이언트의 순번과 이어져야 함).
- 본인에게 `SC_ROOM_CHANGE{레벨 이름, 종류, 채널, 위치, 보정 순번}`.
- 같은 레벨이면 곧바로 ⑦의 "입장 마무리"를, 다른 레벨이면 **로딩 대기**에 둡니다.

⑦ **입장 마무리**:
- 다른 레벨: 클라이언트가 레벨을 열고 `CS_ENTER_ROOM`(지금 패킷 — "로딩 끝났음"으로 다시 씀)을 보낼 때까지 그 플레이어를 시야·전투에 넣지 않습니다(로딩 중에 맞지 않게). `LoadTimeoutSec`(60초, [제안])을 넘기면 접속을 끊습니다.
- 마무리: 본인 `SC_ADD_OBJECT` → `SC_PORTAL_LIST`(그 Room의 포털) → 시야 진입(서로 `SC_ADD_OBJECT`) → 드랍·NPC 시야 → `transfer` 끔.
- **다시 보내지 않는 것**: `SC_INVENTORY`(인벤토리는 바뀌지 않음), 로그인 보정(`pendingEquipFix` — 첫 입장 때만).
- 스킬 쿨타임·아이템 재사용 시간·채팅 간격은 그대로 이어집니다(초기화하지 않음).

⑧ **명부 갱신**: 도착 Room이 서비스에 "이 플레이어가 여기 있음"을 알립니다. 파티원에게 가는 위치 표시(§5-4)가 이때 바뀝니다.

### 4-3. 실패·경합

| 상황 | 처리 |
|---|---|
| 같은 요청이 두 번 | 두 번째는 `transfer`·이동 대기 표시로 무시 |
| ②~④ 사이에 사망 | 이동 취소 |
| ②~⑤ 사이에 접속 해제 | 지금의 퇴장 경로 그대로(출발 Room에서 퇴장). ⑤가 "방에 없음"을 보고 이동을 취소 |
| ⑤와 ⑥ 사이에 접속 해제 | 퇴장 잡이 도착 Room으로 감 → ⑥이 끊긴 세션을 보고 정리, 또는 ⑥ 뒤라면 일반 퇴장 |
| 로딩 대기 중 접속 해제 | 도착 Room의 퇴장 경로가 "로딩 대기 목록"에서 빼고 `NotifyClosedIfDone` |
| 로딩 대기 중 중복 로그인(`SC_KICK`) | 위와 같음(강제 종료 → 퇴장 경로) |
| 도착 인스턴스가 그 사이 소멸 | ⑥을 못 받음 → WorldService가 마을로 다시 보냄(§6-5 닫기 절차가 "예약된 사람이 있으면 닫지 않음"으로 먼저 막음) |

`NotifyClosedIfDone`의 조건("이 방에 없음 + 세션 끊김 + DB 작업 0건")은 그대로 둡니다. 이동 중에는 항상 출발 또는 도착 Room 가운데 한 곳이 그 플레이어의 정리를 맡으므로(위 표) 신호가 빠지지 않습니다. DG3 오류 시험에서 각 구간의 접속 해제를 따로 확인합니다.

### 4-4. 클라이언트

`SC_ROOM_CHANGE`를 받으면:
- **같은 레벨**(마을 ↔ 사냥터): 내 캐릭터를 뺀 모든 원격 캐릭터·몬스터·드랍·NPC 액터를 **지우고**(새 함수 — 지금 `ClearObjects`는 목록만 비우고 액터는 레벨 전환이 지운다고 전제함) 포털 목록을 비운 뒤, 내 캐릭터를 받은 위치로 옮기고 보정 순번을 적용합니다(지금 `OnMyTeleport`와 같은 절차). 열린 상점·거래 창을 닫고 응답 대기 중인 시전(CP1 `PendingCast`)을 버립니다. 로딩 화면은 없습니다. 이어서 오는 `SC_ADD_OBJECT`(내 것은 이미 있으므로 무시)·`SC_PORTAL_LIST`로 새 Room이 채워집니다.
- **다른 레벨**(던전 입장·퇴장): 대기 창을 띄우고 지금의 레벨 전환(`SwitchGameMapLevel`)을 타되 **인벤토리 사본은 비우지 않습니다**(다시 받지 않으므로). 레벨이 열리면 지금처럼 `AJMPlayerController::BeginPlay`가 에셋 예열 뒤 `CS_ENTER_ROOM`을 보냅니다.
- 봇: `SC_ROOM_CHANGE`에서 몬스터·포털 목록을 비우고 위치·순번을 받습니다. 다른 레벨이면 곧바로 `CS_ENTER_ROOM`을 보냅니다.

오브젝트 id: 플레이어(세션 id)·몬스터는 서버 전체에서 유일합니다. 드랍·NPC·거래 번호는 방마다 같은 범위를 쓰지만, 클라이언트가 Room을 옮길 때 전부 지우므로 겹쳐도 됩니다. [그대로]

## 5. 파티

### 5-1. 규칙

- 최대 4명, 파티장 1명, 저장하지 않음, 접속을 끊으면 탈퇴(D-171).
- **같은 채널 사람끼리만** 맺습니다. [결정]
- 초대 방법 [결정]: ① 채팅창에 `/파티초대 이름` ② 1:1 거래처럼 크로스헤어로 상대를 지정해 바로 신청(키는 DG2에서 정함).
- 초대는 파티가 없는 사람 또는 파티장만 할 수 있고(파티가 없던 사람이 초대해 상대가 수락하면 그 사람이 파티장인 파티가 생김), 상대가 이미 파티 중이면 거부됩니다.
- 초대 응답 대기 `PartyInviteTimeoutSec`(30초, [제안]). 한 사람이 받을 수 있는 대기 초대는 1건(다른 초대가 와 있으면 `PARTY_RESULT_TARGET_BUSY`).
- 탈퇴는 언제든. 파티장이 나가면 **가장 먼저 들어온 파티원이 파티장**이 됩니다. [결정] 혼자 남으면 파티가 없어집니다.
- **던전 안에서 파티를 떠나면(탈퇴·접속 해제) 마을로 내보냅니다.** [결정] 추방은 없습니다. [결정]
- 던전 인스턴스 안에 있는 사람은 초대하거나 초대받을 수 없습니다(인스턴스 소유 관계가 꼬이지 않게). 파티에 인스턴스가 있는 동안 밖에 있는 파티장이 새 사람을 초대하는 것은 됩니다 — 그 사람은 입구에서 합류합니다. [제안]
- 더미 봇도 파티를 맺을 수 있습니다(부하 프로필용, 오브젝트 id 지정으로만). [제안]

### 5-2. 상태

`WorldService` 안의 `Party { partyId, leaderUID, members[들어온 순서], instanceId(없으면 0) }`와 `PendingInvite { 받는 사람 UID, 보낸 사람 UID, 만료 시각 }`. 플레이어 쪽에는 `Player::partyId`만 둡니다(Room 잡에서 읽는 사본 — 서비스가 바뀔 때마다 그 플레이어가 있는 Room 잡으로 알려 줌).

### 5-3. 패킷

| 번호 | 패킷 | 내용 |
|---|---|---|
| CS 1035 | `CS_PARTY_INVITE` | `target_id`(오브젝트 id, 0이면 이름 사용), `target_name` |
| CS 1036 | `CS_PARTY_RESPOND` | `accept` |
| CS 1037 | `CS_PARTY_LEAVE` | — |
| SC 2033 | `SC_PARTY_INVITE` | 초대받은 사람에게: 보낸 사람 id·이름, 응답 시간 |
| SC 2034 | `SC_PARTY_STATE` | 파티 전체(파티 번호, 파티장, 파티원 목록: id·이름·레벨·있는 곳 종류). 바뀔 때마다 전원에게. 파티원 0명 = 파티 없음 |
| SC 2035 | `SC_PARTY_RESULT` | 요청 거부(본인에게): `request`(패킷 id) + `PartyResult` |

`PartyResult`: `NO_TARGET`(없음·접속 안 함·자기 자신), `OTHER_CHANNEL`, `TARGET_IN_PARTY`, `TARGET_BUSY`(다른 초대 대기 중), `PARTY_FULL`, `NOT_LEADER`, `IN_DUNGEON`, `DECLINED`, `TIMEOUT`, `NO_INVITE`, `NOT_IN_PARTY`, `TOO_FREQUENT`.

패킷 핸들러는 Room을 거치지 않고 `GWorld->PushJob`으로 서비스에 넘깁니다(파티는 Room 상태가 아님). 초대 빈도는 서비스가 플레이어마다 최소 간격(1초)으로 제한합니다.

### 5-4. 드랍 소유권 [결정: 파티 공유]

- 몬스터를 마지막으로 때린 사람이 파티 중이면 드랍에 그 **파티 번호**도 적습니다(`DropItem::ownerPartyId`). 소유 시간(`DropOwnerSec` 30초) 동안 주울 수 있는 사람 = 막타 본인 또는 **줍는 순간** 같은 파티 번호인 사람. 그 뒤에는 누구나.
- 먼저 주운 사람이 갖습니다(분배 규칙 없음). 골드도 같습니다.
- 드랍이 생긴 뒤 파티를 떠난 사람은 못 줍고, 뒤에 들어온 파티원은 주울 수 있습니다(줍는 순간의 파티 번호로 판정 — 단순하게).
- `DESIGN_ITEMS_TRADE.md`의 "파티·분배는 하지 않음" 문구를 이 규칙으로 고칩니다.

### 5-5. UI (DG2, 최소)

파티 창: 파티원 이름·레벨·있는 곳(마을/사냥터/던전), 파티장 표시, 탈퇴 버튼. 초대 알림은 수락·거절 창(거래 요청 창과 같은 꼴). 결과 안내는 시스템 메시지. HP 막대는 넣지 않습니다(다른 Room의 HP를 실어 나르는 비용 — 필요해지면 따로).

## 6. 인스턴스 던전

### 6-1. 소유

- 인스턴스의 주인은 **파티** 또는 **파티가 없는 플레이어 한 명**입니다(혼자 입장 = 1인 파티로 취급 [결정] — 실제 파티를 만들지는 않고 인스턴스에 주인 UID를 적음).
- 파티 하나에 인스턴스는 하나(`Party::instanceId`), 혼자인 플레이어도 하나.
- 혼자 들어간 사람은 안에 있는 동안 파티를 맺을 수 없습니다(§5-1).

### 6-2. 입장 [결정: 파티장이 같은 Room의 파티원 전원과 함께]

던전 입구 포털 100 반경 안에서 F 키(`CS_PORTAL`, 지금 입력 그대로).

| 요청자 | 인스턴스 | 결과 |
|---|---|---|
| 파티 없음 | 없음 | 새 인스턴스를 만들고 혼자 입장 |
| 파티 없음 | 내 것이 남아 있음(잠깐 나왔다 다시) | 그 인스턴스로 입장 |
| 파티장 | 없음 | 새 인스턴스 + **파티장과 같은 Room(사냥터)에 있는 파티원 전원**이 함께 입장 |
| 파티장 | 있음 | 파티장과 같은 Room에 있는 파티원 전원이 그 인스턴스로 입장 |
| 파티원(파티장 아님) | 있음 | 요청한 본인만 입장(늦게 온 사람의 합류) |
| 파티원(파티장 아님) | 없음 | 거부 `MOVE_RESULT_NOT_LEADER` |

- **같은 Room의 파티원은 모두 함께 갑니다** [결정]: 입구에서 멀리 있어도(파티장만 입구 반경 안이면 됨), 전투·상점·확정 전 거래 중이어도(끊고 옮김), **죽어 있어도**(죽은 채로 도착해 부활하면 던전 시작 지점). 같은 레벨에 있어도 다른 Room(마을)에 있는 파티원은 옮기지 않으며, 나중에 입구로 와서 F로 합류합니다.
- 끝나지 않은 일이 있는 파티원은 §4-2 ②대로 그 사람만 기다렸다가 따라갑니다(다른 사람을 붙잡지 않음). 5초를 넘기면 그 사람만 남고 나중에 합류합니다.
- 인스턴스에 들어올 수 있는 사람은 그 파티원뿐이라 4명을 넘지 않습니다.
- 인스턴스 상한 `MaxDungeonInstances`(서버 전체, [제안] 250 — 채널 500명이 2명씩 들어가는 수)를 넘으면 `MOVE_RESULT_DUNGEON_FULL`. Room 정원과 달리 이 상한은 둡니다: 인스턴스마다 몬스터와 틱이 따로 돌아 수가 곧 서버 비용이고, 측정해 본 적이 없기 때문입니다(DG3c에서 측정해 값을 다시 정함).
- 두 사람이 동시에 요청해도 `WorldService` 잡이 차례로 처리하므로 인스턴스는 한 번만 만들어집니다.

### 6-3. 던전 안 규칙

- 몬스터는 다시 나오지 않습니다(D-171). 데이터: `SpawnTable.RespawnSec` **-1 = 다시 나오지 않음**을 새로 정합니다(0은 지금처럼 "MonsterTable 값 사용"). [제안]
- 시작 지점 = 던전 레벨의 PlayerStart. 그 자리에 **출구 포털**이 있어 언제든 나갈 수 있습니다(§4-1).
- 죽으면 같은 인스턴스의 시작 지점에서 부활합니다(대기 시간·HP 비율은 지금 규칙 — D-149, 패널티 없음). **전원이 죽어도 인스턴스는 그대로**이고 부활해서 이어 갑니다. 정리는 "안에 아무도 없을 때"만 합니다. [결정 — `DESIGN_WORLD.md` §7의 "전원 사망 시 정리" 문구를 고침]
- 안전 구역은 없습니다.
- 클리어: 우두머리가 죽으면 인스턴스를 `CLEARED`로 바꾸고 안의 전원에게 `SC_DUNGEON_STATE{CLEARED, 남은 시간}`. 우두머리 표시는 `SpawnTable`의 구역 이름 `boss`인 스폰으로 정합니다. [제안] `DungeonClearExitSec`(60초, [제안]) 뒤에도 안에 있는 사람은 마을로 내보냅니다. 클리어한 인스턴스에는 새로 들어갈 수 없고(`MOVE_RESULT_DUNGEON_CLEARED`), 전원이 나가면 곧 없어져 파티가 다시 입장하면 새 인스턴스가 만들어집니다.
- 드랍은 §5-4 그대로(혼자면 막타 본인).

### 6-4. 나가기

- 출구 포털: 자기 채널 사냥터 Room의 던전 입구 앞으로.
- 파티 탈퇴·접속 해제·클리어 뒤 시간 종료: 서버가 마을로 보냅니다(접속 해제는 그냥 퇴장).
- 파티가 없어지면(마지막 한 명) 인스턴스의 주인이 그 남은 사람(혼자인 플레이어)으로 바뀝니다 — 혼자 남은 사람이 쫓겨나지 않게. [제안]

### 6-5. 수명과 닫기

- 안에 아무도 없고 들어오는 중인 사람(§4-2 ④)도 없는 상태가 `DungeonEmptyKeepSec`(60초, [제안]) 이어지면 닫습니다(잠깐 나왔다 다시 들어갈 여유).
- 클리어한 인스턴스는 비는 즉시 닫습니다.
- **닫기 절차**(지금 `RoomManager::Remove`는 빈 껍데기이고 예약된 틱이 Room을 계속 살림):
  1. `WorldService`가 인스턴스를 목록에서 빼고(새 입장 불가) Room에 닫기 잡을 넣음.
  2. Room: 닫힘 표시 → 틱이 자기를 다시 예약하지 않음 → 남은 드랍·몬스터·장판 정리 → **잡 큐의 보낼 세션 목록을 모두 내보냄**(`Server/CLAUDE.md` "송신 묶기" 주의 ② — 남기면 그 세션의 송신이 멈춤) → `RoomManager`에서 제거.
  3. 이미 예약된 잡(스킬 판정, 드랍 소멸, 몬스터 제거)은 닫힘 표시를 보고 아무 일도 하지 않습니다. 마지막 예약 잡이 끝나면 Room 메모리가 풀립니다(가장 긴 것 = 드랍 소멸 `DropLifeSec`).
  4. DB 결과 잡은 Room을 붙잡고 있다가 평소대로 처리합니다(플레이어가 방에 없으므로 반영을 건너뛰는 지금 경로 — 단, §4-2 ②로 이동 전에 끝내므로 실제로는 접속 해제 때만 생김).
- 지표: `[metrics]`에 인스턴스 수(지금/만든 수/닫은 수)와 Room 종류별 수.

## 8. 구현 순서 (2026-11-19 재점검, D-219)

### 8-1. 순서를 정한 기준
- **뒤 단계가 기대는 것을 먼저**: 채널·접속자 명부가 없으면 파티("같은 채널만", 이름 초대)를 만들 수 없고, Room 이동이 없으면 던전에 들어갈 수 없습니다.
- **가장 위험한 것을 가장 단순한 조건에서 먼저**: 이 설계에서 가장 위험한 것은 Room 간 이동(접속 해제·사망·DB 작업과의 경합)입니다. 레벨 전환·인스턴스 생성·닫기가 섞이기 전에, 같은 레벨의 마을 ↔ 사냥터에서 먼저 굳힙니다.
- **단계마다 혼자 확인할 수 있게**: 각 단계가 끝나면 서버가 정상 동작하고, 그 단계만의 완료 기준(자동 시험 + 측정)이 있습니다. 동작이 바뀌지 않는 구조 변경은 따로 떼어 "전과 같음"으로 검증합니다.
- **같은 종류의 수정은 한 번에**: 접속 해제 정리(A5.0)는 본 부하 테스트 항목이지만, 이번 작업의 오류 시험(이동 중 접속 해제)과 `_ownerRoom`의 스레드 안전 수정이 같은 코드를 건드립니다. 먼저 해 두면 뒤 단계의 오류 시험을 믿을 수 있습니다.

### 8-3. 이전 초안과 달라진 점과 이유
- **A5.0을 맨 앞으로**: 위 기준 4번째. 규모가 작고 독립적이라 순서를 바꿔도 다른 것을 밀지 않습니다.
- **"DG3a"를 둘로(바탕 / 분할·이동)**: 바탕은 동작이 바뀌지 않아 "전과 같음"만 보면 되고, 분할·이동은 새 동작이라 오류 시험이 큽니다. 한 단계로 묶으면 문제가 났을 때 구조 변경 탓인지 이동 절차 탓인지 가르기 어렵습니다.
- **파티(DG2)는 Room 이동 뒤**: 파티 자체는 바탕(2단계)만 있으면 만들 수 있어 3·4의 순서를 바꿀 수도 있습니다. 그래도 이동을 먼저 두는 이유는 ① 가장 위험한 것을 먼저 굳히기 위해서이고 ② 파티의 "있는 곳 표시"·"던전 안에서 탈퇴하면 마을로"가 Room 이동 위에서 동작하기 때문입니다.
- **던전은 임시 레벨로 먼저**: 서버 절차(DG3c)를 맵 제작(DG4)에 묶지 않습니다. 맵 제작 중에는 서버 시험을 하지 않는다는 기존 방침(`DESIGN_WORLD.md` 제작 순서)과도 맞습니다.
- **경매장은 던전 뒤**: 미루기로 하셨고(2026-11-19), A5.2 전에만 끝나면 됩니다(D-168). 경매 결과가 "요청자의 Room"으로 돌아가는 설계(`DESIGN_ITEMS_TRADE.md`)는 Room 이동이 생긴 뒤에 맞추는 편이 다시 고칠 일이 없습니다.

### 8-4. 단계마다 공통으로 하는 것
- 시작: 코드를 읽고 그 단계의 계획 제시 → 승인.
- 끝: 빌드, 자동 시험(봇·원시 소켓), 부하 회귀(RC2와 같은 조건의 `hunt_250`·`spread_250`), 문서(`Server/CLAUDE.md`·`TESTING.md`), 사용자 PIE가 필요한 것은 `[확인 대기]`.
- 3단계에서 만드는 오류 시험(구간별 접속 해제·사망·중복 요청·DB 지연)은 스크립트로 남겨 5단계에서 다시 씁니다.

## 10. 정해진 것과 남은 제안

**사용자가 정한 것(2026-11-19)**
1. 분할은 포털 기준: 마을 / 사냥터 / 던전 인스턴스.
2. 채널 자동 배정, 선택·변경 없음. **Room별 정원 없음, 채널 500명.**
3. 파티: 같은 채널만, `/파티초대 이름` + 직접 신청, 파티장 자동 위임, 던전 안에서 떠나면 마을로, 추방 없음.
4. 던전 입장: 파티장이 요청하면 같은 Room의 파티원 전원이 함께(파티가 없으면 혼자 = 1인 파티로 취급).
5. 드랍은 파티 공유(먼저 주운 사람 것).
6. 끝나지 않은 일(DB 작업·거래 확정)이 있으면 끝날 때까지 기다렸다 이동.
7. 사냥터에서 죽으면 마을에서 부활, **마을 시작 지점을 여러 곳에 두어 분산**.
8. 던전은 전원이 죽어도 유지, 안에 아무도 없으면 정리.

**남은 제안(승인하면 확정)**
- 수치: 마을 시작 지점 4곳(위치는 DG3b에서 승인), 인스턴스 상한 250(DG3c 측정으로 재확정), 빈 인스턴스 60초 뒤 닫기, 클리어 60초 뒤 내보내기, 초대 응답 30초, 이동 대기 5초, 로딩 60초.
- 규칙: 같은 Room의 죽은 파티원도 함께 입장(도착해서 부활), 파티장이 아니어도 인스턴스가 있으면 혼자 합류 가능, 던전 안에서는 초대 불가, 파티가 한 명만 남으면 인스턴스 주인이 그 사람으로 바뀜, 던전 출구는 사냥터의 입구 앞·서버가 내보내면 마을, 정거장 포털 110은 계속 거부, 채널은 한번 만들면 유지.
- 구조: 전역 서비스 `WorldService` 하나가 명부·채널·파티·인스턴스를 맡음, 요청은 지금의 `CS_PORTAL`·`CS_ENTER_ROOM`을 다시 씀.
- 구현 순서: §8-2(A5.0 → DG3a → DG3b → DG2 → DG3c → DG4 → 경매장).
